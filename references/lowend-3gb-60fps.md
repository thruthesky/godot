# §1. 기초 — 60 FPS 가 무슨 뜻인가

> **왕초보라면 이 절을 꼭 읽으세요.** 뒤의 모든 판단이 여기서 나옵니다.

## 1.1 60 FPS = 한 장을 **16.7밀리초** 안에 끝내기

FPS(Frames Per Second)는 1초에 화면을 몇 장 그리느냐입니다.

```
60 FPS  →  1초 ÷ 60 = 0.0167초 = 16.7 밀리초(ms)
```

**한 장을 16.7ms 안에 못 끝내면 프레임이 떨어집니다.** 이 16.7ms 를 **"프레임 예산"** 이라고 부릅니다.

| 프레임 시간 | FPS | 체감 |
|---|---|---|
| 16.7 ms | 60 | 부드럽다 ✅ |
| 25 ms | 40 | 눈에 띄게 끊긴다 |
| 33 ms | 30 | 확실히 느리다 |

> 💡 **왜 "평균 FPS"만 보면 안 되나** — 평균이 60이어도 가끔 1로 떨어지면 뚝뚝 끊깁니다.
> 그래서 이 문서의 측정은 **최저 FPS도 함께** 기록합니다.

## 1.2 꼭 알아야 할 용어 5개

| 용어 | 쉬운 설명 | 왜 중요한가 |
|---|---|---|
| **드로우콜**<br>(draw call) | GPU 에게 *"이 물건을 여기다 그려라"* 하고 **주문을 한 번 넣는 것** | 주문 횟수가 많으면 주방(CPU)이 바빠집니다 |
| **삼각형**<br>(triangle, tris) | GPU 가 실제로 그리는 최소 도형. **모든 3D 모델은 삼각형 덩어리** | 많을수록 GPU 가 오래 걸립니다 |
| **정점**<br>(vertex) | 삼각형의 꼭짓점 | 캐릭터를 뼈로 움직일 때 **정점마다** 계산합니다 |
| **본**<br>(bone) | 캐릭터를 움직이는 뼈대 | **개수가 곧 CPU 비용**입니다 (§7) |
| **fill rate** | 화면의 **픽셀을 칠하는 속도** | 큰 물체가 화면을 덮으면 비쌉니다 |

> 📖 더 자세한 용어 설명은 [dictionary.md](dictionary.md) 의
> **"삼각형 수 · 폴리곤 수 · 정점 수"** 항목을 보세요.

## 1.3 프레임 하나가 만들어지는 과정

```
    [CPU 가 하는 일]                        [GPU 가 하는 일]

 ① 화면에 뭐가 보이나 추리기      ──▶   ⑥ 삼각형 꼭짓점 위치 계산
 ② 캐릭터 뼈 자세 계산                  ⑦ 삼각형을 픽셀로 쪼개기
 ③ 뼈 위치를 최종 계산                  ⑧ 픽셀에 색칠하기
 ④ 뼈 정보를 GPU 로 보내기
 ⑤ "그려라" 주문 넣기 (드로우콜)
```

**CPU 와 GPU 중 느린 쪽이 프레임을 결정합니다.**
제 경우 **CPU 의 ②③④(뼈 계산)** 가 병목이었고, GPU 는 놀고 있었습니다.

# §2. 게임이 느려지는 이유는 6가지뿐입니다

> **한 줄로 말하면** — 병목은 한 번에 하나만 보입니다. 앞의 것을 풀어야 뒤의 것이 드러납니다.

## 2.1 무엇이 무엇에 비례하는가 (가장 중요한 표)

| # | 단계 | 어디서 | **무엇에 비례하는가** | 제 프로젝트에서 병목이었나 |
|---|---|---|---|---|
| ① | 화면에 뭐가 보이나 추리기 | CPU | **노드 수** | ❌ |
| ② | 애니메이션 자세 보간 | CPU | **캐릭터 수 × 본 수** | ✅ **최대 병목** |
| ③ | 뼈 위치 최종 계산 | CPU | **캐릭터 수 × 본 수** | ✅ **최대 병목** |
| ④ | 뼈 정보 GPU 전송 | CPU→GPU | **캐릭터 수 × 본 수** | ✅ **최대 병목** |
| ⑤ | 드로우콜 제출 | CPU | **주문 횟수**(머티리얼·메시가 바뀔 때마다) | ✅ 초기 병목 |
| ⑥ | 꼭짓점 계산 | GPU | **화면 정점 수** | ✅ 두 번째 병목 |
| ⑦ | 삼각형 → 픽셀 | GPU | **화면 삼각형 수** | ✅ 두 번째 병목 |
| ⑧ | 픽셀 색칠 | GPU | **화면 픽셀 수 × 셰이더 복잡도** | ❌ (조명을 껐더니 여유) |
| ⑨ | 텍스처 읽기 | GPU 대역폭 | **텍스처 크기** | ❌ (압축+밉맵으로 해결) |
| ⑩ | 파일 읽기 | CPU 워커 | **한꺼번에 읽는 개수** | ✅ **앱이 죽는 원인** |
| ⑪ | **메모리 점유** | RAM · VRAM | **정점 데이터 × 복제 수 · 텍스처 크기** | ⚠️ **넘치면 앱이 죽는다** |

## 2.2 제가 만난 병목 6개와 해결 순서

**하나를 풀 때마다 다음 것이 드러났습니다.**

| 순서 | 병목 | 증상 | 어떻게 풀었나 | 결과 |
|---|---|---|---|---|
| 1 | **메모리** | 모델 190종 임포트에 **1.8 GB** | 임포트 전에 텍스처 참조를 뜯어냄 | **9 MB** (200배↓) |
| 2 | **드로우콜** | PC 에서 1,291 · 폰은 로딩도 못 끝냄 | **머티리얼별로 합쳐서 굽기** | **6** (215배↓) |
| 3 | **정점·삼각형** | 54 fps · 해상도 낮춰도 그대로 | 노멀 제거 · 청크 축소 · 거리 컬링 | **60 fps** |
| 4 | **VRAM** | 텍스처 한 장이 16 MB | ETC2 압축 + 밉맵 | **2.67 MB/장** |
| 5 | **본(스켈레톤)** | 캐릭터 30명에서 **40 fps** | **본 65개 → 16개** | **60 fps** |
| 6 | **로딩** | 두세 번에 한 번 앱이 죽음 | 프레임마다 조금씩 읽기 | **5/5 성공** |

## 2.3 ⚠️ 드로우콜은 언제 문제이고 언제 아닌가

**드로우콜이란** GPU 에게 주문을 한 번 넣는 것입니다. 매번 CPU 가 셰이더·텍스처 설정을
바꿔 기록하므로, **주문 횟수가 곧 CPU 비용**입니다.

### 처음에는 최대 병목이었습니다

| 단계 | 드로우콜 | 결과 |
|---|---|---|
| 모듈러 킷 조각마다 노드 하나씩 (PC 측정) | **1,291** | 폰에서는 **조립조차 끝나지 않음** |
| 머티리얼별·청크별로 합친 뒤 | **6** | 60 fps |
| 캐릭터 31명 추가 | 63~83 | 60 fps |

### 하지만 지금은 문제가 아닙니다 — 실측으로 확인

소품 거리 컬링을 풀어 **드로우콜을 일부러 늘려** 봤습니다.

| 조건 | FPS | **드로우콜** | 삼각형 |
|---|---|---|---|
| 기준 | **60.0** | 75 | 101,731 |
| 컬링 해제 | 56.0 | **83** | **155,931** |
| 위 + 애니메이션 정지 | 55.1 | 83 | 155,931 |

**드로우콜은 +8 뿐인데 삼각형이 +53% 늘었고, 애니메이션을 꺼도 55.1 입니다.**
→ 이 구간의 범인은 드로우콜이 아니라 **삼각형**입니다.

### 드로우콜 판단 기준 (A12)

| 드로우콜 | 상태 | 할 일 |
|---|---|---|
| ~100 | 문제없음 | 그냥 두세요 |
| 100~400 | 여유 있음 | 다른 병목을 먼저 보세요 |
| 400~650 | 주의 | 머티리얼 통합 검토 |
| **650~900** | **한계** | 반드시 합치세요 |
| 900+ | 무너짐 | 구조를 다시 짜세요 |

> 🛑 **Godot 의 Mobile 렌더러에는 자동 인스턴싱이 없습니다.**
> Forward+ 는 같은 메시가 연속으로 나오면 하나로 묶어 그리지만(`RenderElementInfo.repeat`),
> **Mobile 의 같은 구조체에는 그 필드 자체가 없습니다**(엔진 소스 확인).
> 그래서 PC 에서 DC 2 인 씬이 폰에서는 **DC 300** 이 됩니다.
> → **개발 PC 의 드로우콜 수치를 절대 믿지 마세요.**

## 2.4 🛑 이 목록에 **없는 것**이 중요합니다

위 어디에도 *"이 모델이 어디서 왔는가"* 는 없습니다.
GPU 는 화면에 올라온 삼각형·픽셀만 세고, CPU 는 존재하는 본과 주문 횟수만 셉니다.

| 하는 일 | 프레임 비용 |
|---|---|
| 모델을 파일 몇 개로 나눴는가 | **무관** |
| 텍스처를 런타임에 갈아 끼웠는가, 미리 구웠는가 | **무관** (→ §7.6 실측) |
| 같은 메시를 공유하는가, 각자 복사본인가 | **무관** (메모리에는 영향) |
| 프로시저럴로 만들었는가, 손으로 만들었는가 | **무관** |

**영향을 주는 것은 오직 "화면에 삼각형·본·픽셀·드로우콜이 몇 개인가" 입니다.**

# §3. ★ 가장 먼저 할 일 — 추측하지 말고 재세요

> **한 줄로 말하면** — 저는 이 작업에서 병목을 **세 번 잘못 짚었습니다.**
> 매번 바로잡아 준 것은 추론이 아니라 **변수를 하나씩 빼서 재는 실험**이었습니다.

## 3.1 방법 — 같은 화면에서 변수를 하나만 바꿉니다

```gdscript
## 한 앱 안에서 조건을 바꿔 가며 순차 측정한다. 조건마다 예열 3초 + 측정 6초.
var sweep_plan := [
    [30, 1.0, {}],                 # 기준
    [30, 1.0, {"scale": 0.6}],     # 픽셀만 줄인다   → fill rate 인가?
    [30, 1.0, {"anim": false}],    # 본 갱신만 멈춘다 → 스켈레톤인가?
    [30, 1.0, {"hide": true}],     # 캐릭터를 지운다  → 렌더인가?
    [0,  1.0, {}],                 # 맵만의 기준선
]
```

**`scaling_3d_scale` 로 픽셀 수만 줄이면 fill rate 인지 아닌지 단번에 갈립니다.**
삼각형·드로우콜·셰이딩은 그대로이기 때문입니다.

## 3.2 실제로 나온 판정 (캐릭터 30명일 때)

| 실험 | FPS | 판정 |
|---|---|---|
| 기준 | 40.3 | — |
| 해상도 60% (픽셀 1/3) | 44.2 | **fill rate 아님** (겨우 +10%) |
| **애니메이션 정지** | **59.8** | ✅ **범인 = 본 계산** |
| 캐릭터 숨김 | 60.0 | 렌더는 문제없음 |

**삼각형도 픽셀도 드로우콜도 아니었습니다.** 이걸 모른 채 폴리곤을 깎았다면 헛수고였습니다.

## 3.3 🛑 측정할 때 반드시 지킬 것 6가지

| 함정 | 실제로 벌어진 일 | 대처 |
|---|---|---|
| **첫 측정을 믿지 마라** | PowerVR 은 셰이더를 "처음 보일 때" 컴파일합니다. 첫 구간이 **1 fps** 로 찍혔습니다 | **9~16초 예열** 후 측정 |
| **화면 캡처가 FPS 를 떨어뜨린다** | `adb screencap` 중에 60 → 1 | 수치는 **파일로 저장해 회수** |
| **드로우콜 수치에 UI 가 섞인다** | `RENDER_TOTAL_DRAW_CALLS_IN_FRAME` 은 3D+UI 합계 | `viewport_get_render_info(vp, TYPE_VISIBLE, ...)` |
| **logcat 은 밀린다** | 삼성 기기는 로그가 많아 결과가 사라집니다 | `user://` 에 쓰고 `adb shell run-as <pkg> cat files/...` |
| **화면이 꺼지면 렌더가 멈춘다** | `dc=0 tris=0 vram=0` 이면 성능 문제가 아닙니다 | `adb shell svc power stayon true` |
| **개발 PC 수치는 무의미** | 같은 씬이 PC 90fps / A12 40fps | 반드시 실기기에서 |

## 3.4 🛑 AI 와 함께 일할 때 — 반드시 되물을 말

**이 문서를 읽는 AI 에게도, AI 에게 묻는 사람에게도 해당한다.**

AI 는 **그럴듯한 추측을 자신 있게 말한다.** 실제로 이 프로젝트에서 AI 는
**fill rate 라고 확신했다가 틀렸고, 삼각형이라고 봤다가 틀렸고, 결국 원인은 본이었다.**
§3.2 의 세 번 오판이 바로 그것이다.

| AI 가 이렇게 말하면 | 이렇게 되묻는다 |
|---|---|
| "아마 삼각형 때문일 겁니다" | **"재봤나요? 뭘 빼서 확인했나요?"** |
| "이렇게 하면 빨라집니다" | **"실기기에서 몇 fps 나왔나요?"** |
| "PC 에서 잘 돕니다" | **"폰에서는요?"** (PC 90fps = A12 40fps) |
| "최적화했습니다" | **"전후 수치를 보여주세요"** |

### AI 쪽에서 지킬 것

**추측을 단정으로 말하지 않는다.** 성능 원인을 말할 때는 셋 중 하나를 함께 낸다.

| 낼 수 있는 것 | 표현 |
|---|---|
| 이 문서의 **실측값** | "§7.2 실측으로는 본 25 → 40.3fps 입니다" |
| **직접 잰 값** | "재보니 전후가 40.3 → 59.8 입니다" |
| 둘 다 없음 | 🛑 **"추측입니다. 재봐야 압니다"** 라고 명시하고, §3.1 의 실험 계획을 제안한다 |

**측정 없이 최적화를 제안하지 않는다.** 원인을 모르는 상태에서 폴리곤을 깎는 제안은
§3.2 에서 헛수고로 판명된 바로 그 경로다.

# §4. 조명 — 광원을 하나도 두지 마세요 (효과 ★★★)

> **한 줄로 말하면** — 저사양에서 조명은 감당이 안 됩니다. **빌드할 때 미리 계산해 색으로 구워 넣습니다.**

## 4.1 실측 — 조명 방식별 FPS

| 방식 | A12 FPS |
|---|---|
| `LightmapGI` (미리 구운 라이트맵) | **1.0** 😱 |
| 실시간 `DirectionalLight3D` 1개 (그림자 없음) | 22.3 |
| **광원 0개 + 정점 컬러에 구운 조명** | **60.0** ✅ |

> 🛑 **흔한 오해** — *"라이트맵은 미리 구워두니 런타임 비용이 0"*.
> **A12 에서는 1.0 fps 입니다.** 텍스처 크기(64KB)도, 포맷도 원인이 아니었습니다.

## 4.2 그럼 어떻게 입체감을 내나 — 정점에 색을 구워 넣습니다

**아이디어**: 조명 계산을 **게임이 켜지기 전에** 해두고, 그 결과를 **꼭짓점의 색**으로 저장합니다.
게임에서는 그 색을 그냥 읽기만 하므로 **비용이 0** 입니다.

```gdscript
## 빌드 타임에 정점마다 조명을 계산해 ARRAY_COLOR 에 넣는다. 런타임 비용 0.
static func shade(world_pos: Vector3, normal: Vector3, lights: Array,
        ao: float = 1.0) -> Color:
    var n := normal.normalized()

    # ① 하늘빛 / 바닥빛 (위를 보는 면은 밝게)
    var up := n.y * 0.5 + 0.5
    var amb := AMBIENT_DOWN.lerp(AMBIENT_UP, up)
    var r := amb.r * ao

    # ② 약한 방향광 — 형태를 읽히게 하는 키라이트 (광원 노드가 아니라 계산값)
    var ndl := maxf(n.dot(-KEY_DIR.normalized()), 0.0)
    r += KEY_COLOR.r * ndl * ao

    # ③ 점광원 — 램프 위치마다. 이것도 노드가 아니라 숫자일 뿐이다
    for l: PointLight in lights:
        var d := l.pos - world_pos
        var dist := d.length()
        if dist > l.radius: continue
        var atten := 1.0 - dist / l.radius
        atten *= atten
        r += l.color.r * atten * maxf(n.dot(d / dist), 0.0) * l.energy

    return Color(minf(r, 1.0), ...)
```

## 4.3 머티리얼은 이 네 줄이 전부입니다

```gdscript
var m := StandardMaterial3D.new()
m.shading_mode = BaseMaterial3D.SHADING_MODE_UNSHADED   ## 픽셀에서 조명 계산 안 함
m.vertex_color_use_as_albedo = true                     ## 정점 색 = 물체 색
m.albedo_texture = tex                                  ## 최종 색 = 텍스처 × 정점 색
m.cull_mode = BaseMaterial3D.CULL_BACK                  ## 뒷면은 그리지 않음
```

## 4.4 그림자 느낌은 격자로 근사합니다 (AO)

정점마다 광선을 쏘면 굽는 데 몇 시간이 걸립니다. 실내에서는
**"벽에 가까운가 · 바닥에 가까운가"** 두 가지만으로 충분히 입체감이 삽니다.

```gdscript
static func ao_from_grid(g: MapGen, wp: Vector3) -> float:
    var cx := int(round(wp.x / MapGen.CELL))
    var cz := int(round(wp.z / MapGen.CELL))
    var open := 0
    for dz in [-1, 0, 1]:
        for dx in [-1, 0, 1]:
            if g.at(cx + dx, cz + dz) == MapGen.EMPTY: open += 1
    var a := 1.0 - float(open) / 9.0 * 0.55                # 벽에 가까울수록 어둡게
    a *= lerpf(0.62, 1.0, clampf(wp.y / 2.2, 0.0, 1.0))    # 바닥 가까이 어둡게
    return a
```

## 5.3 ★ MultiMesh vs 병합 — 메모리를 400배 내는 거래

> **한 줄로 말하면** — 병합은 **"꼭짓점마다 다른 밝기"를 사려고 메모리를 400배 내는 거래**입니다.
> 그 밝기가 필요 없으면 **MultiMesh 가 낫습니다.**
> 🛑 **단 맵 전체를 MultiMesh 하나로 묶으면 안 됩니다** — 컬링과 LOD 가 죽습니다(아래 함정 ①②).

### 🛑 저사양에서는 메모리도 예산이다

드로우콜과 GPU 계산만 보다가 **메모리를 잊으면 안 됩니다.**
3GB 폰에서 쓸 수 있는 메모리는 얼마 되지 않고, 넘치면 **프레임이 아니라 앱이 죽습니다.**

| 저사양의 세 가지 축 | 무엇을 아끼나 |
|---|---|
| ① 드로우콜 | **CPU** 가 주문을 넣는 횟수 |
| ② 삼각형·픽셀 | **GPU** 가 그리는 양 |
| ③ **메모리·VRAM** | **정점 데이터와 텍스처가 차지하는 공간** ← 잊기 쉽다 |

### 메모리 차이가 얼마나 큰가 — 실제 계산

나무 1그루가 삼각형 1,000개 · 정점 600개라고 하면:

```
정점 1개   = 위치 12 byte + UV 8 + 색 16        = 36 byte
나무 1그루 = 정점 600 × 36  +  인덱스 3,000 × 4 ≈ 33 KB
```

**MultiMesh 로 1,000그루**

```
메시 1벌              33 KB
인스턴스 변환 행렬     1,000 × 12 float × 4 byte = 48 KB
──────────────────────────────────────────────────
합계                  약 81 KB
```

**병합으로 1,000그루**

```
정점 데이터가 1,000배로 복제된다
33 KB × 1,000                              ≈ 33 MB
```

# **약 400배 차이입니다.**

병합은 나무 1,000그루의 꼭짓점을 **전부 따로 저장**합니다. 999그루가 첫 그루와
똑같이 생겼어도 그 좌표를 1,000번 적어 둡니다. **그래야 꼭짓점마다 다른 밝기를
넣을 수 있기** 때문입니다.

### 이 프로젝트에서 실제로 낸 대가

```
청크 메시 128개  =  20 MB
```

전부 병합했기 때문입니다. **MultiMesh 였다면 1 MB 도 안 됐을 겁니다.**

20 MB 를 내고 산 것은 **램프 근처의 밝음과 구석의 어둠**이었습니다.
실내 SF 기지라 그 차이가 컸고 메모리 예산에 여유가 있어서 지불할 만했습니다.
**야외에 나무 5,000그루였다면 저도 MultiMesh 를 썼을 겁니다.**

### ★ 판단표

| 조건 | 선택 | 이유 |
|---|---|---|
| 모양·밝기가 전부 같다 | **MultiMesh** | 드로우콜 1 + 메모리 최소 |
| 개수가 아주 많다 (수천 개) | **MultiMesh — 단 청크로 쪼갠다** | 병합하면 메모리가 터진다 · 통으로 묶으면 컬링이 죽는다 |
| 물체마다 **밝기만** 다르면 됨 | **MultiMesh + 인스턴스 색** | 여전히 드로우콜 1 |
| 탄환·파티클처럼 통째로 움직임 | **MultiMesh** | 변환만 다르다 |
| **꼭짓점 단위로 밝기가 달라야 함** | **병합** | 이때만 400배를 지불한다 |
| 서로 다른 모델이 섞임 | **병합** | MultiMesh 는 같은 메시만 |
| **스킨드 캐릭터** | **둘 다 아님** — 개별 노드 | 포즈마다 꼭짓점이 다르다 (아래) |

### 인스턴스 색 — 드로우콜 1을 지키면서 밝기를 주는 법

MultiMesh 는 **인스턴스마다 색 하나씩**을 줄 수 있습니다.

```gdscript
mm.use_colors = true
mm.set_instance_transform(0, xform_a)
mm.set_instance_color(0, Color(1.0, 1.0, 0.9))   # 램프 옆 나무 — 밝게
mm.set_instance_transform(1, xform_b)
mm.set_instance_color(1, Color(0.4, 0.4, 0.5))   # 구석 나무 — 어둡게
```

최종 색은 이렇게 곱해집니다.

```
텍스처  ×  메시의 정점 색  ×  인스턴스 색   =  화면 색
 (무늬)     (형태의 명암)      (이 그루의 밝기)
```

| | 밝기를 몇 개 줄 수 있나 | 드로우콜 | 메모리 |
|---|---|---|---|
| MultiMesh 만 | 1,000그루가 **전부 같은 밝기** | 1 | 최소 |
| **+ 인스턴스 색** | 그루마다 **하나씩** | **1** | +16 byte/인스턴스 |
| 병합 | **꼭짓점마다** | 머티리얼 수 | **400배** |

**작은 물체는 인스턴스 색으로 충분합니다.** 물체 전체가 비슷한 밝기여도 어색하지 않기
때문입니다. 큰 물체(건물·긴 벽)는 한쪽만 밝게 할 수 없어 부족합니다.

### 🛑 "그럼 가능한 건 전부 MultiMesh 로 하면 되지 않나?"

**메모리만 보면 그 말이 맞습니다.** 위치·회전·크기가 제각각이어도 드로우콜은 1이고,
구운 에셋 파일도 함께 작아집니다. 그런데 MultiMesh 에는 **잘 안 적혀 있는 함정이 셋**
있습니다. 셋 다 메모리가 아니라 **GPU 와 프레임을 무너뜨립니다.**

#### 함정 ① 컬링이 "전부 아니면 전무" 다 ← 가장 위험

Godot 공식 문서의 원문입니다.

> there is no *screen* or *frustum* culling possible for individual instances.
> This means, that millions of objects will be *always* or *never* drawn

MultiMesh 는 **인스턴스 하나하나를 따로 잘라내지 못합니다.** 통째로 상자(AABB) 하나로
보고, 그 상자가 화면에 걸치면 **안에 든 것을 전부 그립니다.** 카메라 뒤에 있어도 그립니다.

```
[맵 전체를 MultiMesh 1개로 — 나무 5,000그루]
  화면에 보이는 것은 100그루
  → 5,000그루가 전부 GPU 로 간다        ❌ 50배를 헛그린다

[청크마다 MultiMesh 1개]
  화면에 걸친 청크 3개만 그린다
  → 약 150그루                          ✅
```

공식 문서가 내놓는 해법도 같습니다 — **"세계의 영역별로 MultiMesh 를 여러 개 만들라."**

#### 함정 ② LOD 가 MultiMesh 하나당 한 번만 정해진다

성능을 위해 **LOD 선택은 MultiMesh 단위**로 수행되고, 그 안의 인스턴스는 전부 같은
LOD 를 씁니다. 맵 전체를 하나로 묶으면 **발밑의 나무와 지평선의 나무가 같은 삼각형 수**로
그려집니다. 원거리를 싸게 그리려고 만든 LOD 가 통째로 무력해집니다.

> ### 🛑 단 이 게임은 **직교 투영**이라 함정 ②가 성립하지 않는다
>
> 카메라가 `PROJECTION_ORTHOGONAL` 고정입니다([SSOT §1](../../game/references/SSOT.md)).
> **직교에서는 거리가 LOD 에 아무 영향도 주지 않으므로**([PR #57419](https://github.com/godotengine/godot/pull/57419)
> 에서 직교면 거리를 상수 `1.0` 으로 고정), **MultiMesh 로 묶든 안 묶든 화면의 모든
> 물체가 어차피 같은 LOD** 입니다. 잃는 것이 없습니다.
>
> **그래도 청크 분할은 계속합니다** — 함정 ①(컬링)과 ③(삼각형)은 그대로이고,
> **①이 애초에 가장 큰 이유**였습니다. 상세는
> [lowend-culling-lod.md §3](lowend-culling-lod.md).


#### 함정 ③ 삼각형은 1개도 줄지 않는다 ← 이 프로젝트의 실제 병목

**MultiMesh 가 줄이는 것은 "주문 횟수"지 "그리는 양"이 아닙니다.**
나무 1,000그루 × 500삼각형 = 50만 삼각형은, 드로우콜이 1이어도 그대로 50만입니다.

이 프로젝트의 실측이 정확히 그 장면입니다.

| | 드로우콜 | 삼각형 | FPS |
|---|---|---|---|
| 기준 | 75 | 101,731 | 60 |
| 기물 추가 후 | 83 (**+8**) | 155,931 (**+53%**) | **56** |

드로우콜은 8밖에 안 늘었는데 4프레임을 잃었습니다. **범인은 삼각형이었습니다.**
MultiMesh 로 묶었더라도 이 4프레임은 똑같이 잃습니다.

#### 결론 — 쓴다. 단 "청크로 쪼개서" 쓴다

| | 드로우콜 | 컬링 | LOD | 메모리 |
|---|---|---|---|---|
| 맵 전체를 MultiMesh 1개 | **1** | ❌ 전부 그림 | ❌ 하나로 통일 | ✅ 최소 |
| **청크마다 MultiMesh** | 청크 수 | ✅ 된다 | ✅ 청크별 | ✅ 최소 |
| 병합 | 머티리얼 수 | ✅ 된다 | ✅ | ❌ **400배** |

**가운데 줄이 정답입니다.** 드로우콜 1을 지키자고 컬링과 LOD 를 버리면 손해입니다.
청크 하나에 수십~수백 개가 들어가므로 드로우콜은 이미 충분히 적습니다.

> **청크 크기의 기준** — 이 프로젝트의 청크는 32 m (§5.2) 입니다. 화면에 동시에
> 걸치는 청크가 **4~9개**가 되도록 잡으면, 헛그리는 양과 드로우콜이 함께 낮게 유지됩니다.

### 🛑 스킨드 캐릭터는 MultiMesh 로 묶이지 않는다

**"움직이는 것"이 기준이 아닙니다. "꼭짓점이 각자 다르게 움직이는가"가 기준입니다.**

```
탄환 100개    메시가 같고 위치·회전만 다르다        →  묶인다  ✅
캐릭터 100명  A는 걷고 B는 공격하고 C는 서 있다
              → 꼭짓점 위치가 전부 다르다           →  안 묶인다  ❌
```

Godot 의 MultiMesh 는 스켈레톤을 지원하지 않습니다. 실측이 이를 보여줍니다.

```
캐릭터 31명 × (몸 + 무기) = 62
실측 드로우콜 63~83  ←  거의 그대로 나갔다
```

#### 그럼 캐릭터 100명을 1 드로우콜로 그릴 수는 없나 — VAT

**Godot 의 기본 기능으로는 불가능합니다.** 다만 방법이 아주 없지는 않습니다.
**VAT(Vertex Animation Texture)** 는 애니메이션의 **모든 프레임을 텍스처에 미리 구워 두고**,
셰이더가 그것을 읽어 꼭짓점을 옮기는 기법입니다.

```
[일반 스킨드 메시]
  CPU 가 뼈를 계산 → GPU 로 전송 → 정점 이동
  → 캐릭터마다 드로우콜

[VAT]
  텍스처에 "3번 프레임의 꼭짓점 위치들" 이 저장되어 있다
  셰이더가 그것을 읽어 정점을 옮긴다
  → 뼈 계산 0 · MultiMesh 로 묶임 → 드로우콜 1
```

| | 일반 스킨드 | **VAT** |
|---|---|---|
| 드로우콜 (100명) | 100 + | **1** |
| CPU 본 계산 | **있음** (이 프로젝트의 최대 병목) | **없음** |
| 구현 난이도 | 낮음 | **높음** — 커스텀 셰이더 + 굽는 도구 |
| 애니메이션 블렌딩 | 자유롭다 | **어렵다** (프레임을 미리 구웠으므로) |
| 텍스처 메모리 | 없음 | 애니메이션 × 프레임 × 정점 만큼 |

**모바일 군중 렌더링의 표준 기법**이지만 이 프로젝트에서는 쓰지 않았습니다 —
**본을 16개로 줄이는 것만으로 60fps 가 나왔기** 때문입니다.

> 💡 **판단 기준** — 캐릭터가 **100명 이상** 필요하면 VAT 를 검토한다.
> **30명 규모라면 본 수를 줄이는 쪽(§7)이 훨씬 간단하고 확실합니다.**

#### 정리 — 무엇을 MultiMesh 로 묶을 수 있나

```
✅ 묶인다 — 모양이 같고 "변환" 만 다른 것
   탄환 · 파티클 · 풀 · 돌 · 나무 · 상자 · 코인

❌ 안 묶인다 — "꼭짓점" 이 각자 움직이는 것
   스킨드 캐릭터 · 몬스터 · 천 시뮬레이션
   (VAT 같은 특수 기법을 쓰면 가능하지만 구현이 크다)
```

**탄환은 통째로 날아가므로(변환) 묶이고, 캐릭터는 팔다리가 따로 움직이므로(정점) 안 묶입니다.**

### 기물 종류별 권장

기물은 대체로 **자연물과 인공물**로 나뉘고, 성격이 달라 선택도 갈립니다.

| 분류 | 예 | 특징 | 권장 |
|---|---|---|---|
| **자연물** | 나무 · 풀 · 바위 · 돌멩이 · 수풀 | **같은 모양이 대량 반복** · 개체가 작다 | **MultiMesh** (+ 인스턴스 색) |
| **지형** | 언덕 · 절벽 · 바닥 | 하나하나가 유일하고 넓다 | **병합** (조명 대비가 크다) |
| **인공물(소형)** | 상자 · 배럴 · 램프 · 표지판 | 반복되지만 실내 조명을 받는다 | **MultiMesh + 인스턴스 색** |
| **인공물(대형)** | 집 · 건물 · 오두막 · 성벽 | 크고 종류가 다양 · **창문/그늘 대비 중요** | **병합** |
| **캐릭터·몬스터** | PC · NPC | 포즈가 각자 다르다 | **개별 노드** (본 수를 줄인다 → §7) |

> 💡 **한 맵에서 둘을 섞어 쓰는 것이 정상입니다.**
> 이 프로젝트는 실내라 전부 병합했지만, 야외 맵이라면
> **지형·건물은 병합 · 나무와 바위는 MultiMesh** 로 갔을 것입니다.

    var key := [chunk, s["bucket"], is_prop]
    ...
    for i in nv:

## 5.7 🛑 굽기에서 실제로 걸린 함정 6개

| 함정 | 증상 | 해결 |
|---|---|---|
| **헤드리스에서 `MultiMesh.set_instance_transform()` 이 무시됨** | **에러도 경고도 없이** 빈 채로 저장(파일 416 B, AABB 0) | `mm.buffer` 에 `PackedFloat32Array` 를 **직접 대입**. 읽을 때도 `buffer` 를 봅니다 |
| 청크 경계에 격자 자국 | 경계에서 노멀이 틀림 | 이웃 높이를 배열에서 clamp 하지 말고 **노이즈를 직접 샘플링** |
| 물체가 새까맣게 나옴 | 삼각형 감는 방향(winding)으로 노멀 반전 | `(c - a).cross(b - a)` 방향 확인 |
| 인덱스 캐스팅 오류 | non-indexed 메시는 `ARRAY_INDEX` 가 null | null 검사 후 순번으로 대체 |
| **`.json`/`.txt` 가 APK 에 없음** | 런타임에 `get_as_text()` 가 null | `export_presets.cfg` 에 `include_filter="*.json,*.txt"` |
| **프로젝트 안의 `.blend` 가 임포트를 막음** | "Blender path is invalid" 로 **전체 임포트 중단** | 임시 폴더에 `.gdignore` 파일 |

## 6.1 🛑 glTF 임포터는 텍스처를 모델마다 복제합니다

| | 값 |
|---|---|
| 원본 | 모듈러 킷 190종 · 정점 데이터 5.5 MB · 공용 텍스처 21장 |
| **그냥 임포트** | **1.8 GB** — 모델 하나가 **30 MB** (같은 텍스처가 190벌 복제) |
| 머티리얼을 뜯어낸 뒤 | **9 MB** (200배 감소) |

**해결** — 임포트 **전에** gltf 파일에서 머티리얼 참조를 지우고, 텍스처는 프로젝트에서 한 벌만 관리합니다.

```python
# 어떤 머티리얼이었는지는 JSON 에 따로 기록해 두고, 참조만 지웁니다.
surf = []
for m in d.get('meshes', []):
    for p in m['primitives']:
        mi = p.pop('material', None)
        surf.append(d['materials'][mi]['name'] if mi is not None else '')
mapping[name] = surf
for k in ('materials', 'textures', 'images', 'samplers'):
    d.pop(k, None)
```

## 6.2 머티리얼 21종 → 9개로 줄이기

**텍스처가 같으면 한 덩어리로 모으고**, 단색은 정점 색에 흡수시킵니다.

```gdscript
func bucket_of(mat_name: String) -> String:
    var d: Dictionary = mat_defs.get(mat_name, {})
    var tex: String = d.get("tex", "")
    if tex == "": return BUCKET_SOLID              ## 단색 → 정점 색으로 흡수
    if d.get("mask", false): return tex + "#mask"  ## 알파는 따로
    return tex
```

## 6.3 반드시 바꿔야 하는 임포트 설정

| 항목 | 기본값 | **바꿀 값** | 왜 |
|---|---|---|---|
| Normal · ORM · Emissive 텍스처 | 다 임포트 | **버립니다** | UNSHADED 는 읽지 않습니다 |
| `compress/mode` | `0`(무압축) | **`2`(VRAM)** | 2048² 한 장이 GPU 에서 **16 MB → 2.67 MB** |
| `mipmaps/generate` | `false` | **`true`** | 3D 에는 필수. 없으면 멀리서 지글거립니다 |
| `compress/hdr_compression` | `1` | **`0`** | **A12 에서 앱이 죽는 것을 막습니다** |
| `doubleSided`(양면) | 켜짐 | **`CULL_BACK`** | 뒷면까지 그리면 픽셀을 2배 씁니다 |
| `meshes/ensure_tangents` | `true` | **`false`** | 정점당 16 byte 절약 |
| `meshes/create_shadow_meshes` | `true` | **`false`** | 광원이 0개입니다 |

> ⚠️ **UV 타일링을 쓰는 모델은 텍스처를 하나로 합칠 수 없습니다.**
> 제 킷은 190종 중 81종이 UV 가 0~1 을 벗어났고(타일링), 아틀라스로 합쳤다면 다 깨졌을 겁니다.

# §7. 캐릭터 30명 이상 띄우기 — 병목은 "본"입니다

> 그래서 캐릭터 최적화는 **묶는 것이 아니라 하나하나를 가볍게 하는 것**입니다

| 10,000 | 144,380 | 52.2 ❌ |

**본 16개 기준으로 캐릭터 삼각형을 3배 올려도 60fps 가 유지됩니다.**
디테일이 부족하면 **본부터 확인하고, 그 다음 삼각형을 올리세요.**

### 🛑 "삼각형 2만 개 이하면 얼굴이 뭉개진다" — 라리엔 3D 에서는 성립하지 않습니다

**들으신 적이 있을 수 있습니다. 그 말은 조건이 빠져 있습니다.**
원근 투영 게임에서는 맞을 수 있습니다 — 캐릭터에 다가가면 얼굴이 화면을 가득 채우니까요.
**라리엔 3D 는 직교 투영 고정이라 다가가도 커지지 않습니다**
(→ [SSOT §2](../../game/references/SSOT.md), [용어집 · LOD](dictionary.md#lod-level-of-detail--멀면-단순한-모델로-바꿔-그린다)).

그래서 이 프로젝트에서는 **"삼각형이 몇 개면 되는가"를 취향이 아니라 픽셀로 답할 수 있습니다.**

#### 실측 ① 얼굴은 화면에서 **최대 38 × 36 픽셀**입니다

SSOT 규격 그대로(직교 · 피치 −45° · `keep_aspect = KEEP_HEIGHT`) 카메라를 세우고,
키 1.8 m · 얼굴 0.15 × 0.20 m 로 렌더해 **픽셀을 직접 세었습니다.**

| 화면 · 줌 | `size` | 1 m = | 캐릭터 전체 높이 | **얼굴 픽셀** | 얼굴 가로×세로 |
|---|---|---|---|---|---|
| 모바일 1080×1920 · 기준 | 15 | 128 px | 175 px | **360 px²** | 20 × 18 |
| 모바일 · **줌 최대 확대** | 7.5 | 256 px | 349 px | **1,368 px²** | **38 × 36** ← 최대 |
| 모바일 · 줌 최대 축소 | 30 | 64 px | 87 px | 90 px² | 10 × 9 |
| 데스크톱 1920×1080 · 기준 | 22.5 | 48 px | 66 px | 56 px² | 8 × 7 |
| 데스크톱 · 줌 최대 확대 | 11.25 | 96 px | 131 px | 182 px² | 14 × 13 |

**얼굴이 가장 크게 보이는 순간이 38 × 36 픽셀입니다.** 아이콘 하나 크기입니다.

> 🛑 **이 값은 모델과 무관합니다.** 직교 투영에서 화면 크기를 정하는 것은
> 카메라 `size` 와 해상도뿐입니다. 어떤 캐릭터를 넣어도 얼굴은 이 픽셀 수입니다.

#### 실측 ② 머리 삼각형 **1,024개**를 넘으면 화면이 **픽셀 단위로 같아집니다**

같은 머리 형상(지름 0.23 m)을 **삼각형 수만 바꿔** 렌더하고,
앞 단계와 **몇 픽셀이 달라졌는지** 1:1 로 비교했습니다.

| 머리 삼각형 | 기준 줌 (머리 680 px²) | 최대 확대 (머리 2,708 px²) |
|---|---|---|
| 64 → 144 | 84 px 달라짐 | 311 px |
| 144 → 256 | 27 px | 116 px |
| 256 → 576 | 34 px | 68 px |
| 576 → **1,024** | **2 px** | 23 px |
| 1,024 → 2,304 | **1 px** | 6 px |
| 2,304 → 4,096 | **0 px** ← 완전히 동일 | 5 px |
| 4,096 → 9,216 | **0 px** | 4 px (2,708 중 **0.15%**) |

**기준 줌에서는 머리 2,304개를 넘는 순간 화면이 한 픽셀도 달라지지 않습니다.**
최대 확대에서도 2,304개를 넘으면 차이가 **0.2% 미만**이라 눈으로 구분할 수 없습니다.

#### 그래서 캐릭터 예산은 이렇게 나옵니다

사람 캐릭터는 머리에 전체 삼각형의 **15~25%** 를 씁니다(얼굴이 중요하니까요).
위 포화점을 캐릭터 전체로 환산하면:

| 포화점 | 머리 삼각형 | **캐릭터 전체 환산** | 이 프로젝트의 값 |
|---|---|---|---|
| 기준 줌에서 포화 | 1,024 | **4,000 ~ 6,800** | **NPC 5,000** ✅ |
| 최대 확대에서 포화 | 2,304 | **9,200 ~ 15,400** | **플레이어 15,000** ✅ |
| "2만 개" 주장 | 3,000 ~ 5,000 | 20,000 | ❌ **화면에 나타나지 않음** |

**§7.1 의 5,000 / 15,000 이 픽셀 실측과 정확히 맞아떨어집니다.**
2만 개는 **더 예쁜 것이 아니라, 보이지 않는 곳에 프레임을 쓰는 것**입니다.
삼각형 1개가 화면 **0.68 픽셀**이 되어 픽셀보다 작아집니다.

> ⚠️ **컷신·연출은 예외입니다.** 자유 카메라로 얼굴을 클로즈업하면 전제가 무너집니다.
> 그때는 컷신 전용 고밀도 모델을 따로 쓰고, 평상시 모델은 위 예산을 지킵니다.

#### 🛑 그럼 얼굴이 실제로 뭉개지는 원인은 무엇인가

**삼각형 총량이 아닙니다.** 실제 원인은 셋이고, 셋 다 총량을 올려도 낫지 않습니다.

| 진짜 원인 | 증상 | 고치는 곳 |
|---|---|---|
| **① 배분** — 무기·장비가 예산을 독식 | 얼굴에 삼각형이 **거의 안 남는다** | 파트별로 **세어서** 배분 (§7.1) |
| **② 텍스처** — 얼굴 UV 영역이 작다 | 총량을 올려도 흐릿한 그대로 | UV 에서 **얼굴에 넓게** 배정 |
| **③ 감축 방식** — 균등 decimate | 곡률이 완만한 **얼굴이 먼저 깎인다** | 얼굴에 **가중치를 주어** 감축 |

**②가 특히 자주 오진됩니다.** 얼굴이 20 × 18 픽셀로 보이므로 텍스처에서 얼굴 영역은
밉맵을 감안해 **40 × 40 px 이상**이면 충분합니다. 그보다 흐리다면 해상도가 아니라
**UV 배분**이 문제입니다 — 1024² 텍스처에 얼굴이 30 px 로 들어가 있는 식입니다.

#### 이 프로젝트의 실제 에셋에서 확인한 것 (2026-09-02)

`assets/actor/pc/male/male.glb` 의 삼각형을 GLB 원본에서 직접 세었습니다.

| 프리미티브 | 삼각형 | 크기 | 정체 |
|---|---|---|---|
| 0 | **234** (4.9%) | 8.70 × 1.80 × 10.03 m | **캐릭터 몸통 전체** |
| 1 | **4,564** (95.1%) | 1.27 × 0.42 × 5.18 m | **검 한 자루** |
| | **4,798** | | |

**머리(정수리~0.23 m)에 남은 삼각형은 1개, 얼굴에는 0개입니다.**

> 🛑 **얼굴이 뭉개진다면 이것이 원인입니다.** 총량 4,798 은 예산 안이지만
> **95%가 검 한 자루에 들어가 있어** 몸통에 234개밖에 남지 않았습니다.
> 총량을 2만으로 올려도 같은 비율이면 얼굴은 여전히 **1,000분의 5**입니다.
> → §7.1 의 경고("오브젝트 이름을 믿지 말고 폴리곤 수를 직접 세라")가
> **이 에셋에서 그대로 재현되고 있습니다.**

**고치는 순서** — ① 검을 **234개 수준으로** 감축한다(직선 위주라 크게 깎아도 티가 안 납니다)
② 확보한 예산을 몸통·얼굴에 준다 ③ 다시 세어 확인한다.

**재현 방법** — GLB 는 프리미티브마다 `POSITION` accessor 에 `min`/`max` 가 들어 있어
Blender 를 열지 않고도 파트별 크기·삼각형 수를 셀 수 있습니다.

```python
# GLB 의 파트별 삼각형 수와 크기를 세는 최소 코드
import json, struct
with open(path, 'rb') as f:
    f.read(12)
    clen, _ = struct.unpack('<II', f.read(8))
    js = json.loads(f.read(clen))
for i, prim in enumerate(js['meshes'][0]['primitives']):
    tris = js['accessors'][prim['indices']]['count'] // 3
    a = js['accessors'][prim['attributes']['POSITION']]
    size = [round(a['max'][k] - a['min'][k], 2) for k in range(3)]
    print(f"프리미티브 {i}: 삼각형 {tris:,}  크기 {size} m")
```


## 7.6 장비·외형 교체 — 프레임 비용과 무관합니다

MMORPG 는 같은 캐릭터가 장비만 바꿔 입습니다. 두 가지 길이 있습니다.

| | **A. 모델 1개 + 런타임 교체** | B. 조합마다 미리 굽기 |
|---|---|---|
| 3D 모델 파일 | 1개 | 조합 수만큼 |
| **FPS** | **차이 없음** | **차이 없음** |
| 메모리 · VRAM | 적다 | 많다 |
| 조합 확장 | 무제한 | **불가능** |

**실측** — 같은 캐릭터 31명을 두 방식으로:

| 방식 | FPS | 메모리 | VRAM |
|---|---|---|---|
| GLB 5종 (메시 5벌) | **60.0** | 53.3 MB | 102.6 MB |
| **GLB 1종 + 텍스처 5장** | **60.0** | **52.4 MB** | **96.6 MB** |

**결론은 A 입니다 — 성능이 아니라 확장성 때문입니다.**
갑옷 10종 × 무기 10종이면 조합이 100개입니다. B 는 모델 100개를 구워야 하지만
**A 는 텍스처 20장이면 끝납니다.**

```gdscript
## 🛑 surface_set_material 로 원본 메시를 고치면 모든 인스턴스가 함께 바뀝니다.
##    override 는 인스턴스별로 적용되고 메시는 한 벌로 공유됩니다.
body.set_surface_override_material(0, body_mat)
```

### ⚠️ 단, "텍스처 교체" 와 "메시 부착" 을 구분하세요

| 방식 | 프레임 비용 |
|---|---|
| **텍스처만 교체** (같은 메시, 다른 색) | **증가 없음** ← 위 실측 |
| **부위 메시 추가** (헬멧·어깨보호구를 별도 메시로) | **드로우콜 +N · 삼각형 +N** |

장비가 실루엣을 바꿔야 하면 메시를 붙일 수밖에 없고, 그때는 **비용이 실제로 늘어납니다.**

## 7.8 glTF 머티리얼은 그대로 쓰면 안 됩니다

임포트 직후 실측: `transparency = 4`(알파 뎁스 프리패스) · `cull_mode = 2`(양면).

# §8. 앱이 죽지 않게 — 파일을 한꺼번에 읽지 마세요

> **한 줄로 말하면** — `_ready()` 에서 전부 `load()` 하면 드라이버가 죽습니다.

## 8.1 증상

청크 159개 + 캐릭터 31개를 한꺼번에 읽으면 Godot 이 워커 스레드에 작업을 쏟아붓고,
그 와중에 PowerVR 드라이버가 **`SIGSEGV`** 로 죽었습니다. **두세 번에 한 번 재현**됐습니다.

## 8.2 해결 — 프레임마다 조금씩 읽습니다

```gdscript
enum { L_CHUNKS, L_PLAYER, L_NPCS, L_WARM, L_DONE }
const LOAD_PER_FRAME := 4      ## 한 프레임에 읽는 리소스 수

func _process(dt):
    if load_phase != L_DONE:
        _load_step()           # 조금씩만 읽습니다
        return
    ...

func _load_step():
    match load_phase:
        L_CHUNKS: ...  hud.text = "맵 %d%%" % pct
        L_NPCS:   ...  hud.text = "캐릭터 %d%%" % pct
        L_WARM:
            ## 🛑 셰이더는 "처음 화면에 보일 때" 컴파일됩니다. 캐릭터 31개가
            ##    한꺼번에 나타나면 그 순간 드라이버가 몰립니다. 줌을 넓혀
            ##    몇 프레임 보여 주며 미리 컴파일시킨 뒤 게임 줌으로 돌아갑니다.
            zoom = 2.0
            if warm_frames > 90: zoom = 0.4; load_phase = L_DONE
```

**결과: 5회 연속 실행 성공(5/5).**
덤으로 검은 스플래시 대신 **"맵 62% → 캐릭터 40% → 준비 중"** 진행률이 보입니다.

## 8.3 그 밖의 크래시 원인

| 원인 | 증상 | 해결 |
|---|---|---|
| **ASTC HDR 텍스처** | `Image format ASTC_4x4_HDR not supported` → 즉시 종료 | `compress/hdr_compression=0` |
| 머티리얼 반복 수정 | 셰이더 재컴파일 폭주 | §7.8 참조 |
| 셰이더 첫 컴파일 | 첫 실행 최대 **100초** 멈춤 | 캐시가 쌓이면 7초. 예열 구간을 두세요 |

- [ ] `compress/mode=2`(VRAM) 인가
- [ ] `mipmaps/generate=true` 인가
- [ ] `compress/hdr_compression=0` 인가 ← **앱 죽음 방지**
- [ ] Normal·ORM·Emissive 를 버렸는가

## 캐릭터
- [ ] 본이 **20개 이하**인가
- [ ] `transparency=DISABLED` · `cull_mode=CULL_BACK` 로 덮어썼는가
- [ ] 머티리얼을 인스턴스마다가 아니라 **메시당 한 번** 고치는가
- [ ] 안 보이는 캐릭터의 `AnimationMixer.active` 를 끄는가

## 로딩·안정성
- [ ] 리소스를 프레임에 나눠 읽는가
- [ ] 셰이더 예열 구간이 있는가

## 측정
- [ ] **Mobile 렌더러**로, **실기기**에서, **예열 후**에 쟀는가
- [ ] 결과를 파일로 남겨 회수하는가 (logcat 은 밀립니다)
- [ ] 병목을 **변수를 빼는 실험**으로 확인했는가 ← **추측 금지**
