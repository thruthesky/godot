# 용어집 — Godot·3D 개발 용어

Godot 문서·에디터 UI·이 스킬의 다른 참조 문서에 그대로 나오는 용어를 **뜻 → 왜 그렇게
부르는가 → 라리엔 3D 에서 실제로 어떻게 쓰는가** 순으로 정리한다.
"이름은 봤는데 무엇인지 모르겠는" 상태를 없애는 것이 이 문서의 목적이다.

용어를 설명하면서 나온 API·기본값은 **엔진에서 직접 추출해 확인한 것**이며,
확인 기준은 `godot --version` 기준 **4.7.2.stable** 이다.

```bash
godot --headless --doctool /tmp/gddoc     # 클래스 정의 XML 전체 추출
```

## 지오메트리 (geometry) — 형상 그 자체

**모양을 이루는 데이터**를 가리키는 말이다. 수학의 기하학(geometry)에서 그대로 온 이름이고,
3D 에서는 **정점(vertex)·모서리(edge)·면(face)** 으로 이루어진 형태를 뜻한다.

**핵심은 "무엇이 빠져 있는가"다.** 색·무늬·광택·조명은 지오메트리가 아니다.
회색 상자뿐인 블록아웃 맵을 두고 **"지오메트리는 다 됐다"** 고 말할 수 있는 이유가 이것이다.

| 지오메트리다 | 지오메트리가 아니다 |
|---|---|
| 정점 좌표, 면을 잇는 순서(인덱스) | 텍스처·머티리얼 (색·거칠기·금속성) |
| [노멀](#노멀-normal--면이-향한-방향)(면이 향한 방향), [UV](#uv-언랩-uv-unwrap--펼치는-작업) 좌표 | 조명·그림자·라이트맵 |
| 벽·바닥·계단·기둥의 **형태** | 파티클·UI·사운드·카메라 |

### 두 가지 넓이로 쓰인다 — 문맥으로 가른다

같은 단어가 크기가 다른 두 가지를 가리킨다. **이것이 헷갈리는 주된 이유다.**

| | 뜻 | 이렇게 쓴다 |
|---|---|---|
| **① 데이터로서** | 메시 하나 안에 든 정점·면 배열 | "이 건물은 지오메트리가 640 삼각형이다" |
| **② 레벨 구성물로서** | 맵을 이루는 **움직이지 않는 구조물 전체** | "레벨 지오메트리", "**정적 지오메트리**(static geometry)" |

②의 뜻일 때 **캐릭터·몹·아이템은 지오메트리에 넣지 않는다.** 그것들은
**액터(actor)·프롭(prop)** 이라 부른다. 그냥 "지오메트리"라고 하면 대개
**움직이지 않아서 굽기·병합·컬링의 대상이 되는 것**을 가리킨다고 보면 맞다.

### Godot 에서 이 단어를 만나는 세 곳

**1. `GeometryInstance3D` — "형상을 그리는 3D 노드"의 공통 조상** (엔진에서 확인)

```
Node3D
└─ VisualInstance3D          화면에 무언가 기여하는 3D 노드
   ├─ GeometryInstance3D     ← 그중 "형상을 그리는" 것
   │  ├─ MeshInstance3D          메시 하나
   │  ├─ MultiMeshInstance3D     같은 메시를 대량으로
   │  ├─ CSGShape3D              ← CSG 도 여기 속한다
   │  ├─ GPUParticles3D · CPUParticles3D
   │  └─ Label3D · SpriteBase3D
   ├─ Light3D · Decal · ReflectionProbe · LightmapGI · VoxelGI
   └─ OccluderInstance3D · FogVolume
```

`Light3D`·`Decal`·`ReflectionProbe` 는 `VisualInstance3D` 까지만 상속하고
**`GeometryInstance3D` 에는 들어오지 않는다.** 빛과 데칼은 화면에 영향을 주지만
**형상을 그리지는 않기 때문**이다. 이 갈림이 곧 "지오메트리"라는 말의 경계다.

**렌더 예산에 직결되는 속성이 전부 이 클래스에 있다** (기본값은 엔진에서 확인):

| 속성 | 기본값 | 무엇 |
|---|---|---|
| `cast_shadow` | `1` (ON) | 그림자를 드리우나 |
| `gi_mode` | `1` (STATIC) | 라이트맵에 구울 대상인가 |
| `lod_bias` | `1.0` | LOD 전환 거리 배율 |
| `visibility_range_begin` / `end` | `0.0` | 거리별 표시 구간 (0 = 제한 없음) |
| `visibility_range_fade_mode` | **`0` (DISABLED)** | 🛑 **켜지 않으면 LOD 가 툭 바뀐다** ([SSOT §4](../../game/references/SSOT.md)) |
| `material_override` | `None` | 머티리얼 통째 교체 |
| `transparency` | `0.0` | 0 = 불투명 |

**2. 씬 구조의 `Geometry` 노드 — 관례적인 이름이다**

Godot 이 정한 이름이 아니라 **레벨 디자인 관례**로 붙이는 이름이다.
[level-design.md](level-design.md) 의 권장 구조에서 이 자리가 **②의 뜻**으로 쓰인다.

```
Level (Node3D)
├─ Geometry (Node3D)      ← 벽·바닥 메시 + 콜리전. 움직이지 않는 것
├─ NavigationRegion3D     길찾기 — 베이크 대상이 위 Geometry 다
├─ Props (Node3D)         소품. 지오메트리와 섞지 않는다
└─ SpawnPoints (Node3D)
```

**`Props` 를 `Geometry` 안에 넣지 않는 이유가 여기서 나온다** — 내비메시 베이크가
"지오메트리"를 대상으로 도는데, 나무·상자까지 딸려 들어가면 길이 잘못 파인다.

**3. `Geometry3D` 는 노드가 아니다 — 이름만 비슷하다**

`Geometry3D` 는 `Object` 를 상속하는 **정적 계산 함수 모음**이다 (엔진에서 확인).
씬에 배치할 수 없고, 형상을 담지도 않는다.

```gdscript
Geometry3D.ray_intersects_triangle(...)      # 광선이 삼각형과 만나는가
Geometry3D.get_closest_point_to_segment(...) # 선분 위 가장 가까운 점
```

`Geometry2D` 도 같은 성격의 2D 판이다. **`GeometryInstance3D` 와 혼동하지 않는다.**

### 라리엔 3D 에서

| 어디 | 지오메트리가 하는 일 |
|---|---|
| **CSG → 아트 교체 지점** | `Geometry` 노드 안의 것을 통째로 갈아끼운다. [CSG 의 제약](#반드시-알아야-할-제약--csg-는-최종물이-아니다) |
| **드로우콜 예산** | 정적 지오메트리는 **청크당 20~30 DC** ([SSOT §3](../../game/references/SSOT.md)). 메시 병합·`MultiMesh` 로 달성한다 |
| **라이트맵** | 지오메트리가 확정돼야 굽는다. 형상이 바뀌면 다시 굽는다 |
| **용량** | 파일 크기를 정하는 것은 **텍스처**이지 지오메트리가 아니다. 640 삼각형 건물이 **4.1 KB** 다 |

**"폴리곤을 줄여야 하나?"의 답이 여기 있다** — 지오메트리는 생각보다 싸다.
비싼 것은 텍스처와 드로우콜이다.

## CSG — Constructive Solid Geometry

우리말로 **"구성적 입체 기하"**. 3D 모델링 기법의 이름이다.

기본 도형(상자·구·원기둥)을 **불리언 연산으로 합치고 빼서** 형태를 만드는 방식이다.
점과 면을 하나하나 찍어 만드는 폴리곤 모델링(Blender 방식)과 정반대의 접근이다.

### 연산은 딱 3가지

`CSGShape3D.operation` 속성의 값이며, **기본값은 Union(`OPERATION_UNION` = 0)** 이다.

| 연산 | 상수 | 값 | 결과 |
|---|---|---|---|
| Union (합집합) | `OPERATION_UNION` | 0 | 두 도형을 붙여 하나로 |
| Intersection (교집합) | `OPERATION_INTERSECTION` | 1 | 겹치는 부분만 남김 |
| Subtraction (차집합) | `OPERATION_SUBTRACTION` | 2 | 앞 도형에서 뒤 도형을 파냄 |

진짜 값어치는 **Subtraction** 에 있다. 벽 상자에서 작은 상자를 빼면 → **문이 뚫린다.**
원기둥을 빼면 → **창문이 뚫린다.** Blender 를 열지 않고 **Godot 에디터 안에서 바로**
되는 것이 핵심이다.

### CSG 노드 계층 (엔진에서 확인)

```
CSGShape3D                 ← 베이스. 직접 배치하지 않는다
│                            (operation·use_collision·bake_* 는 전부 여기 있다)
├─ CSGCombiner3D           여러 CSG 를 묶는 컨테이너
└─ CSGPrimitive3D          도형 공통 베이스. 직접 배치하지 않는다 (flip_faces)
   ├─ CSGBox3D             상자      size = Vector3(1, 1, 1)
   ├─ CSGSphere3D          구        radius = 0.5, radial_segments = 12, rings = 6
   ├─ CSGCylinder3D        원기둥    radius = 0.5, height = 2.0, sides = 8
   │                                 cone = true 로 원뿔
   ├─ CSGTorus3D           도넛      inner_radius = 0.5, outer_radius = 1.0
   ├─ CSGPolygon3D         2D 다각형을 밀어내기
   │                                 mode = MODE_DEPTH(0) 압출 / MODE_SPIN(1) 회전
   │                                        / MODE_PATH(2) Path3D 따라 밀기
   └─ CSGMesh3D            기존 메시를 CSG 재료로
```

씬에 실제로 놓는 것은 **7종**(`CSGCombiner3D` + 프리미티브 6종)이고,
`CSGShape3D`·`CSGPrimitive3D` 는 속성을 물려주는 베이스라 배치하지 않는다.

> ⚠️ **`use_collision` 기본값은 `false` 다.** 켜지 않으면 만든 벽을 그대로 통과한다.
> 블록아웃을 걸어다니며 확인하려면 **최상위 `CSGCombiner3D` 에서 한 번만** 켠다.
> (`collision_layer`·`collision_mask` 기본값은 각각 `1`)

### `CSGShape3D` 의 속성 — 전부 여기서 물려받는다 (실측 기본값)

씬에 놓는 7종은 아래 값을 공통으로 갖는다. `CSGBox3D` 인스턴스에서 직접 읽은 값이다.

| 속성 | 기본값 | 무엇 |
|---|---|---|
| `operation` | `0` (Union) | 위의 세 연산 |
| `use_collision` | **`false`** | 🛑 **켜야 벽이 벽이 된다** |
| `collision_layer` · `collision_mask` | `1` · `1` | 충돌 레이어 |
| `collision_priority` | `1.0` | 침투 해소 우선순위 |
| `snap` | `0.001` | 정점을 이 간격으로 맞춰 **면이 정확히 겹칠 때 생기는 오차**를 흡수한다 |
| `calculate_tangents` | `true` | 노멀맵용 탄젠트 생성 |
| `autosmooth` | `false` | 켜면 `smoothing_angle`(`50.0`) 보다 완만한 모서리를 부드럽게 |
| `flip_faces` | `false` | (`CSGPrimitive3D`) 면 뒤집기 |

> **`CSGShape3D` 는 `GeometryInstance3D` 를 상속한다** (엔진에서 확인).
> 즉 CSG 도 일반 메시와 똑같이 그림자·LOD·표시 거리 속성을 갖는다
> → [지오메트리](#지오메트리-geometry--형상-그-자체)

## 블록아웃 (blockout) — 회색 상자 단계

레벨 디자인 용어다. **그레이박싱(greyboxing)**, **화이트박싱**이라고도 부른다.

텍스처도 아트도 없이 **회색 상자만으로 레벨의 구조·동선·크기감을 먼저 짜는 단계**를
말한다. 건축의 종이 모형, 웹 디자인의 와이어프레임과 정확히 같은 위치에 있다.

### 왜 이 단계를 따로 두는가

| 이유 | 내용 |
|---|---|
| **재미는 아트가 아니라 공간 배치에서 나온다** | 통로가 답답한지, 몹이 한 곳에 몰리는지, 엄폐물 간격이 맞는지는 회색 상자로도 전부 판단된다 |
| **고치는 비용이 0 이다** | 아트를 다 만든 뒤 "통로를 2m 넓혀야겠다"가 되면 벽·바닥·조명·라이트맵·내비메시를 전부 다시 만들어야 한다. 블록아웃 단계면 상자 크기만 바꾸면 끝이다 |
| **직접 걸어봐야 안다** | 위에서 본 도면과 캐릭터 눈높이에서 느끼는 공간감은 완전히 다르다 |

## "CSG 블록아웃" — 두 개를 합친 말

**"CSG 노드로 블록아웃을 한다"**는 뜻이다.

Godot 에서 블록아웃하는 방법은 세 가지가 있는데, CSG 를 고르는 이유는 하나다 —
**구멍을 뚫을 수 있는 건 CSG 뿐이다.**

| 방법 | 문·창문 뚫기 | 비고 |
|---|---|---|
| `MeshInstance3D` + `BoxMesh` | ❌ 불가 | 콜리전도 손으로 |
| **CSG** | ✅ Subtraction | **블록아웃 표준** |
| `GridMap` | ❌ | 타일(MeshLibrary)이 이미 있어야 함 |

### 실제 씬 구조

```
Level (Node3D)
└─ CSGCombiner3D          use_collision = ON   ← 콜리전은 여기서 한 번만
   ├─ CSGBox3D  Floor      size (20, 0.5, 20)   Union
   ├─ CSGBox3D  WallNorth  size (20, 3, 0.5)    Union
   ├─ CSGBox3D  Doorway    size (1.2, 2.2, 2)   Subtraction  ← 벽에 문 구멍
   └─ CSGBox3D  Pillar     size (0.5, 3, 0.5)   Union
```

`Doorway` 를 `WallNorth` 와 겹치게 놓고 연산을 **Subtraction** 으로 바꾸면 벽에 문이 뚫린다.
빼는 도형은 뷰포트에서 **빨간 와이어프레임**으로 표시돼 헷갈리지 않는다.

## 첫 맵은 왜 "무조건" CSG 블록아웃인가

**"첫 맵은 무조건 CSG"** 라는 말에는 **강제성이 다른 두 주장**이 붙어 있다.
나눠서 봐야 어디까지가 규칙이고 어디부터가 선택인지 보인다.

| 주장 | 실제 강제성 |
|---|---|
| ① **블록아웃 단계를 거친다** (회색 상자로 동선·크기를 먼저 검증) | 🛑 **사실상 필수.** 건너뛰면 되돌리는 비용이 폭발한다 |
| ② **그 블록아웃을 CSG 로 한다** | ✅ **첫 맵에는 사실상 유일한 실용적 선택** — 원리적 필연은 아니다 |

즉 정확히는 **"무조건 블록아웃이고, 첫 맵의 블록아웃 도구로는 CSG 말고 쓸 만한 게 없다"** 이다.

### 왜 첫 맵에서는 CSG 말고 대안이 없나

블록아웃 후보는 셋인데 **첫 맵에서는 나머지 둘이 탈락한다.**

| 방법 | 문·창문 뚫기 | 첫 맵에서 탈락하는 이유 |
|---|---|---|
| `MeshInstance3D` + `BoxMesh` | ❌ 불가 | 벽에 문을 낼 수 없고, 콜리전도 하나씩 손으로 붙여야 한다 |
| **CSG** | ✅ Subtraction | — |
| `GridMap` | ❌ | **타일(`MeshLibrary`)이 이미 있어야 한다.** 첫 맵에는 그 타일이 아직 없다 |

**CSG 만 가진 것은 둘이다.**

- **빼기 연산** — 동선 병목은 대부분 **문 폭**에서 생기는데, 그것을 검증하려면 문이 뚫려 있어야 한다
- **콜리전 한 번에** — 최상위 `CSGCombiner3D` 에서 `use_collision` 한 번이면 끝난다.
  **"만들자마자 걸어본다"** 가 성립하는 이유다

`GridMap` 은 **CSG 로 치수 검증이 끝난 뒤** 그 치수대로 타일을 만들어 넘어가는
다음 단계이지, 첫 맵의 대안이 아니다.

### 라리엔 3D 에서 특히 되돌리기가 비싼 이유

일반적인 3D 게임보다 **블록아웃 생략이 더 치명적이다.**
[SSOT](../../game/references/SSOT.md) 의 결정들이 전부 **"지오메트리 확정"을 전제로 하기 때문**이다.

| SSOT 결정 | 지오메트리가 바뀌면 |
|---|---|
| **§2 조명을 전부 굽는다** (동적 조명 없음) | 벽 하나 옮길 때마다 **라이트맵 재베이크**. 릴리즈는 최고 품질로 굽는다 = 오래 걸린다 |
| **§3 드로우콜 ~300**, 메시 병합·`MultiMesh` 전제 | 병합은 형상 확정 후에만 가능하다. 확정 전 아트는 **병합도 못 하고 다시 만든다** |
| **§5 청크 250m, 라이트맵도 청크 단위** | 인접 청크를 포함해 굽고 잘라내므로 **이웃 청크 재베이크까지** 부른다 |
| **§1 카메라 −45° 고정** | 화면에 방 전체가 들어와 **크기 감각이 현실과 다르다** (기준 12×12m → [방(room)](#방-room--맵의-구획-단위)) |
| **§1 가림 해법 1순위 = 레벨 디자인 회피 (비용 0)** | **동선 위에 시야를 막는 구조물을 두지 않는 것**이 최선책인데, 이건 회색 상자를 **걸어봐야만** 판정된다. 아트를 만든 뒤 발견하면 2순위(반투명 페이드) 비용을 영구히 낸다 |

CSG 단계는 이 모든 것이 **아직 붙기 전**이다. 그래서 마음껏 부술 수 있고, 그게 존재 이유다.

### 모든 맵에서 필수는 아니다 — CSG 를 쓰지 않는 경우

**"모든 게임 맵에 CSG 가 필요한가"의 답은 아니오다.** 필수인 것은 *블록아웃*이고,
도구는 상황에 따라 갈린다.

| 상황 | CSG 를 쓰지 않는 이유 |
|---|---|
| **타일이 확정된 뒤의 두 번째·세 번째 던전** | 검증된 방 모듈이 `MeshLibrary` 에 있으면 `GridMap` 으로 바로 찍는 게 빠르다. **이때는 GridMap 배치 자체가 블록아웃을 겸한다** |
| **야외 사냥터·필드** | 구조가 "넓은 바닥 + 지형 기복 + 경계 산맥"이라 **뚫을 벽이 없다.** CSG 의 유일한 강점인 Subtraction 이 쓰이지 않는다. 랜드마크·경계 덩어리 정도만 CSG 로 잡는다 |
| **1.25km 넘는 오픈월드** | 크기와 청크 구획을 먼저 정하는 것이 우선이다 → [openworld-3d.md](openworld-3d.md). 순서를 바꾸면 만든 것을 다시 만든다 |
| **구매·외주로 형상이 확정된 맵 (glTF 통짜)** | 검증할 대상이 이미 없다. 단, **동선이 라리엔에 맞는지는 여전히 걸어서 확인한다** |
| **프롭만 재배치하는 갱신** | 구조가 바뀌지 않는다 |

> **한 줄로** — CSG 가 특별해서 필수인 게 아니라, **"싸게 부술 수 있는 형상"이 필수**이고
> Godot 에서 첫 맵에 그것을 제공하는 것이 CSG 뿐이다.

## 레벨 (level) — 맵 한 판

> 🛑 **캐릭터 레벨(Lv. 30)이 아니다.** 철자도 발음도 같지만 완전히 다른 말이다.
> MMORPG 를 만들 때 이 둘이 같은 프로젝트 안에서 동시에 쓰이므로 가장 헷갈리는 용어다.

**게임 한 판이 벌어지는 공간 하나**를 뜻한다. 쉽게 말해 **맵 한 개**다.

- 던전 하나 = 레벨 하나
- 사냥터 하나 = 레벨 하나
- 마을 하나 = 레벨 하나
- 슈퍼마리오의 "1-1", "1-2" = 레벨

### 왜 하필 "레벨(층)"이라고 부르는가

초기 게임이 **던전의 층**을 하나씩 내려가는 구조였기 때문이다(로그라이크, 이후 Doom).
1층을 깨면 2층으로 — 그래서 공간 한 판을 **level(층)** 이라 불렀고,
게임이 층 구조를 벗어난 뒤에도 **"공간 한 판"** 이라는 뜻만 남아 굳었다.

한국 게임업계에서는 **"맵"** 이라고 더 많이 부른다. 영어 문서·엔진 UI 에서는 **level**
이 표준어라, 문서를 읽을 때 이 둘을 같은 것으로 놓고 읽으면 된다.

| 한국에서 | 영어 문서에서 | 같은 것인가 |
|---|---|---|
| 맵 | level / map | ✅ 사실상 같다 |
| 스테이지 | stage / level | ✅ 같다 (스테이지는 "순서가 있는 판" 뉘앙스) |
| 존(zone) | zone | 🟡 **서버가 나눈 단위**. 라리엔에서는 이쪽이 별도 개념이다 |

### "레벨"이 들어간 말들 — 전부 "맵"으로 바꿔 읽으면 된다

| 용어 | 뜻 | 바꿔 읽으면 |
|---|---|---|
| **레벨 디자인** | 맵의 구조·동선·난이도를 설계하는 일 | **맵 설계** |
| **레벨 에디터** | 맵을 만드는 편집 도구 | **맵 편집기** |
| **레벨 지오메트리** | 맵을 이루는 움직이지 않는 구조물 (벽·바닥·계단) | **맵 형상** |
| **레벨 스트리밍** | 맵을 조각내 필요한 부분만 읽어 들이는 것 | **맵 스트리밍** |
| **블록아웃 / 그레이박싱** | 회색 상자만으로 맵 구조를 먼저 짜는 단계 | → [블록아웃](#블록아웃-blockout--회색-상자-단계) |

### 🛑 함정 — **LOD 의 L 도 level 인데 뜻이 완전히 다르다**

**LOD = Level of Detail(디테일의 수준)** 이다. 여기서 level 은 **"맵"이 아니라 "정도·수준"**
이라는 일상적인 뜻이다. 멀리 있는 물체를 단순한 모델로 바꿔 그리는 최적화 기법을 가리킨다.

| 같은 "level" 이지만 | 뜻 |
|---|---|
| 레벨 디자인, 레벨 에디터 | **맵** |
| **L**evel **o**f **D**etail (LOD) | **수준·정도** |
| 캐릭터 레벨 (Lv. 30) | **등급** |

셋을 구분하는 방법은 간단하다 — **앞뒤 단어를 본다.** `of Detail` 이 붙으면 최적화,
`디자인·에디터·스트리밍`이 붙으면 맵, `Lv.` 나 숫자가 붙으면 캐릭터 성장이다.

### 엔진마다 부르는 이름이 다르다

| 엔진 | 맵 한 판을 부르는 이름 | 파일 |
|---|---|---|
| **Godot** | **"레벨"이라는 개념 자체가 없다.** 그냥 **씬(scene)** 이다 | `.tscn` |
| Unity | 씬(Scene) | `.unity` |
| Unreal | **레벨(Level)** — 실제 클래스 이름이 `ULevel` 이다 | `.umap` |

> 🔍 **엔진에서 확인** — Godot 4.7.2 의 클래스 **1,076개 중 이름에 `Level` 이 들어간 것은
> 0개**다(`--doctool` 로 추출해 확인). 즉 Godot 문서에서 "레벨"을 검색해도 아무것도 안 나온다.
> **Godot 에서 맵을 찾으려면 "씬(scene)"으로 찾아야 한다.**

Godot 이 레벨을 따로 두지 않는 이유는 **맵도 프리팹도 전부 같은 `.tscn` 씬**이기 때문이다.
나무 한 그루도 씬이고, 그 나무 100그루가 심긴 사냥터도 씬이다. 차이는 **크기와 용도뿐**이며
엔진은 둘을 구분하지 않는다 → [basics.md](basics.md).

### 라리엔 3D 에서

씬 골격에 **`Level` 이라는 이름의 노드**가 있다
([level-design.md](level-design.md) 0단계).

```
Main (Node3D)
├─ WorldEnvironment
├─ DirectionalLight3D
├─ Level (Node3D)      ← 이것
├─ Player
└─ CameraRig
```

> 🛑 **이 `Level` 은 엔진이 정한 이름이 아니라 우리가 지은 이름이다.**
> `Map` 이나 `World` 로 바꿔도 아무 문제가 없다. 다만 코드에서 `$Level` 로 찾고 있다면
> 같이 고쳐야 한다 → [example.md](example.md) 의 "`$` 는 이름으로 찾는다".

이 노드를 둔 이유는 **맵을 통째로 갈아끼우는 자리**를 하나로 정해 두기 위해서다.
자식 하나를 지우고 새 맵 씬을 붙이면 맵 전환이 끝나고, 조명·카메라·플레이어는
`Main` 에 그대로 남는다.

그리고 라리엔에서 **레벨(맵)과 존(zone)은 다른 것**이다.

| | 뜻 | 정하는 쪽 |
|---|---|---|
| **레벨 = 맵** | 클라이언트가 그리는 공간 한 판 | 클라이언트 |
| **존(zone)** | **서버가 나눈 단위.** 존이 바뀌면 접속이 옮겨간다 | **서버** |

던전이 별도 맵인 이유가 여기 있다 — 실내로 걸어 들어가는 것이 아니라
**서버 존 전환을 거친다** → [design.md](../../game/references/design.md) 결정 1.

## 방 (room) — 맵의 구획 단위

**게임 맵에서 사방이 막힌 공간 한 칸**을 부르는 말이다. 침실·거실 같은 집의 방이 아니라
**맵을 구성하는 구획 단위**를 뜻한다. 영어 레벨 디자인 문서의 **room** 을 그대로 옮긴 말이다.

이런 것을 전부 "방"이라고 부른다.

- 던전의 몬스터 방
- 보스 방
- 창고, 복도, 광장
- 실내 어디든 벽으로 둘러싸인 한 칸

"맵을 만들려면 먼저 방을 하나 만드세요"라고 할 때의 방은
**용도가 아직 정해지지 않은 회색 빈 공간**이다. 던전 방이 될 수도, 마을 창고가 될 수도,
그냥 지워질 수도 있다. 처음 만드는 방의 목적은 단 하나 —
**CSG 로 바닥 깔고 → 벽 세우고 → 문 뚫는 조작을 손에 익히는 것**이다.

### 크기 감각 — 현실보다 훨씬 크게 잡는다

연습용 기준 치수는 **12 × 12 m** 다. 약 **43평**, 학교 교실 2개 정도 크기다.
현실의 방보다 훨씬 크게 잡는 데는 이유가 있다.

| 이유 | 내용 |
|---|---|
| **캐릭터가 빠르다** | 게임 캐릭터의 이동 속도는 초당 4~5m 다. 현실 사람의 보행(초당 약 1.4m)의 3배가 넘는다 |
| **위에서 내려다본다** | 카메라 피치가 고정된 쿼터뷰라 화면에 방 전체가 들어온다. 좁으면 그대로 답답해 보인다 |
| **전투 여유가 필요하다** | 몬스터 몇 마리가 들어와 싸우고, 플레이어가 피할 공간이 남아야 한다 |

**현실 크기로 만들면 게임에서는 거의 항상 너무 좁게 느껴진다.**
방을 처음 만들 때 가장 흔한 실수가 이것이다.

### 실내인가 야외인가 — 구조가 완전히 갈린다

**방을 쌓는 방식은 실내 맵에만 맞는다.** 맵을 짜기 전에 어느 쪽인지 먼저 정한다.

| 맵 종류 | 구조 | 만드는 법 |
|---|---|---|
| **실내** (던전·건물) | **방 + 복도** | 벽으로 칸을 나누고 문으로 잇는다. CSG Subtraction 으로 문·창문을 뚫는다 |
| **야외** (사냥터·필드) | **넓은 바닥 + 지형 기복 + 경계 산맥** | 벽으로 막지 않는다. 지형 높이로 동선을 만들고 맵 끝은 산맥·절벽·물로 자연스럽게 닫는다 |

야외를 방처럼 벽으로 두르면 **보이지 않는 벽에 갇힌 느낌**이 나고,
실내를 야외처럼 트면 **길을 잃는다.** 어느 쪽이든 **CSG 로 상자를 놓는 조작 자체는 같으므로**,
연습으로 12×12 방을 한 번 만들어 보는 것은 야외 맵을 만들 사람에게도 값어치가 있다.

맵 제작 방식 전체와 씬 골격은 [level-design.md](level-design.md) 를 본다.

## 피치 · 요 · 롤 — 카메라 회전 3축

**항공 용어에서 온 이름**이다. 비행기가 도는 세 방향을 그대로 3D 카메라·오브젝트에 쓴다.
**셋 다 "회전"이고, 줌은 여기 속하지 않는다.**

```
        pitch (피치) — 고개를 끄덕이는 방향
              ↕   위를 보다 / 아래를 보다

   yaw (요) — 고개를 젓는 방향   ↔   왼쪽을 보다 / 오른쪽을 보다

   roll (롤) — 고개를 갸웃하는 방향   ↻   화면이 기울어진다
```

| 용어 | 회전축 | 사람 몸으로 치면 | 게임에서 |
|---|---|---|---|
| **yaw** (요) | **Y축**(수직) | 고개를 **좌우로 젓기** — 도리도리 | 맵을 빙 돌려 본다 |
| **pitch** (피치) | **X축**(좌우) | 고개를 **위아래로 끄덕이기** | 위에서 내려다보거나 지평선을 본다 |
| **roll** (롤) | **Z축**(전후) | 고개를 **어깨 쪽으로 갸웃** | 화면이 기운다. 게임에선 거의 안 쓴다 |

**줌(zoom)은 회전이 아니다.** 카메라가 대상에서 **멀어지거나 가까워지는 것**(또는 화각을
바꾸는 것)이라 **각도는 그대로고 보이는 범위만 넓어지고 좁아진다.**

### Godot 에서

`Node3D` 의 `rotation` 은 라디안 단위 오일러 각이고 **`(x, y, z)` 가 곧 (pitch, yaw, roll)** 이다.
에디터 인스펙터의 `Rotation` 은 도(degree)로 보여준다.

```gdscript
$Camera3D.rotation_degrees = Vector3(-45, 0, 0)    # pitch −45° = 비스듬히 내려다봄
$Camera3D.rotation_degrees = Vector3(-45, 90, 0)   # 거기서 yaw 90° = 옆에서 본다
```

> ⚠️ 값을 읽고 쓰는 것은 되지만 **회전을 누적할 때 오일러를 쓰면 안 된다** —
> 짐벌락·회전 순서 의존이 생긴다. 누적은 `Transform3D`/`Basis`/`Quaternion` 으로 한다
> ([3d-core.md](3d-core.md)).

### 왜 피치가 더 비싼가 (고정 시점 게임에서)

**yaw 는 옆으로 돌 뿐이라 "보이는 거리"가 변하지 않는다. 피치는 보이는 거리가 변한다.**

| 축을 풀면 | 결과 |
|---|---|
| **yaw** | 지물의 뒷면을 만들어야 한다 (아트 물량 증가). 보이는 거리는 그대로 |
| **pitch** | 카메라를 눕히면 **지평선이 보이고**, 낮추면 **캐릭터에 가까워진다.** 원거리 처리(스카이박스·LOD·임포스터)의 전제가 통째로 깨진다 |

라리엔 3D 의 카메라 정책과 그 수치 근거는
[game 스킬의 realism-openworld.md](../../game/references/realism-openworld.md) §5 에 있다.

## 텍스처 (texture) — 표면을 펼쳐 만든 이미지

**3D 모델의 표면을 통째로 벗겨 평면으로 펼친 뒤, 거기에 그림을 그려 둔 이미지 파일**이다.
**픽셀 하나하나가 각자의 색을 가진다.**

> **종이 상자로 생각한다.** 상자를 칼로 갈라 평면으로 펼치면 십자 모양이 나온다.
> 그 펼친 종이에 그림을 그려 두고 다시 접어서 상자로 만드는 것 — 이것이 텍스처다.

3D 모델은 **형태**(정점의 위치)만 가지고 있다. 색은 형태에 들어 있지 않다.
그래서 "이 정점은 텍스처의 어느 지점에 해당하는가"를 따로 적어 두는데,
그 좌표를 **UV 좌표**라고 부른다.

### UV 언랩 (UV unwrap) — 펼치는 작업

3D 표면을 2D 평면으로 펼쳐 UV 좌표를 정하는 작업이다. Blender 에서 한다.
`X`·`Y`·`Z` 는 이미 3D 좌표에 쓰고 있으므로 **텍스처 쪽 축은 `U`·`V` 로 부른다.**
그게 이름의 전부다.

| | |
|---|---|
| **UV1** | 색·요철 텍스처를 붙이는 기본 좌표 |
| **UV2** | **라이트맵 전용 좌표.** 겹치는 부분이 없어야 해서 UV1 과 따로 만든다 |

### "맵(map)"은 텍스처의 **종류**를 가리키는 말이다

전부 그냥 이미지 파일이고, **담긴 내용이 다를 뿐**이다.

| 이름 | 담은 것 | Godot `StandardMaterial3D` |
|---|---|---|
| **컬러맵 / 알베도맵** | 색 | `albedo_texture` |
| **노멀맵** | 표면 요철 → [노멀맵](#노멀맵-normal-map--표면-요철을-텍스처에-담은-것) | `normal_texture` |
| **러프니스맵** | 거칠기(반들거림) | `roughness_texture` |
| **메탈릭맵** | 금속인가 아닌가 | `metallic_texture` |
| **AO 맵** | 구석의 그늘 | `ao_texture` |
| **하이트맵** | 높낮이 | `heightmap_texture` |

**PBR 3장**이라고 하면 보통 **알베도 + 노멀 + ORM**(Occlusion·Roughness·Metallic 을
한 이미지의 R·G·B 채널에 욱여넣은 것)을 말한다. 3장을 쓰는 이유는 색만으로는
실사가 되지 않고 **빛이 어떻게 반사되는지**가 필요하기 때문이다.

### 왜 텍스처 파일이 그렇게 커지는가

**"색 값 하나만 저장하면 되지 않나"는 절반 맞다.** 단색이면 실제로 거의 0 이다.
256×256 이미지 세 장을 만들어 PNG 로 저장해 **직접 재 본 결과**다.

| 이미지 내용 | 파일 크기 |
|---|---|
| ① 완전 단색 | **761 바이트** |
| ② 큰 색 영역 4개 (체크무늬) | **817 바이트** |
| ③ 픽셀마다 미세하게 다름 (실사) | **87,743 바이트** |

**①과 ②는 사실상 같다.** PNG 압축이 "이 색 × 1만 픽셀" 로 줄여서 저장하기 때문이다.
**갈라지는 지점은 ③이고, 115배가 된다.**

**그러므로 텍스처가 큰 진짜 이유는 "3D"가 아니라 "실사"다.**

벽돌 벽 사진을 떠올린다. 벽돌마다 색이 미묘하게 다르고, 같은 벽돌 안에서도 얼룩과
균열과 그늘이 있다. **바로 그 미세한 차이가 "실사로 보이는" 정체**인데, 그건 곧
**인접 픽셀끼리 색이 다르다**는 뜻이고 **압축이 줄일 게 없다**는 뜻이다.

| 단색이면 | 텍스처 자체가 필요 없다. `albedo_color` 값 하나면 되고 **0 바이트** |
|---|---|
| **실사면** | 픽셀마다 다르므로 **픽셀 수만큼** 저장해야 한다 |

### "좌표 범위 + 색상"으로 저장하면 안 되나 — 그것이 벡터 그래픽이다

*"어느 좌표부터 어느 좌표까지 이 색"* 이라고만 적는 방식은 실제로 존재한다.
**SVG(벡터 그래픽)** 가 정확히 그것이다. 게임 텍스처로 쓰지 않는 이유는 둘이다.

| 이유 | 내용 |
|---|---|
| **실사는 영역으로 안 나뉜다** | 벽돌 사진을 "같은 색 영역"으로 쪼개면 영역 개수가 픽셀 수에 근접한다. 영역마다 좌표 4개 + 색 3바이트를 쓰면 **오히려 원본보다 커진다** |
| **GPU 가 픽셀을 직접 읽는 하드웨어다** | 텍스처 샘플링 회로가 물리적으로 박혀 있어 UV 좌표를 주면 색을 즉시 뱉는다. 벡터라면 픽셀마다 "내가 어느 영역인가"를 계산해야 하는데 **화면 200만 픽셀 × 60프레임 × 영역 수백 개**다. 저사양 모바일에서는 불가능하다 |

### 128px · 256px · 512px 은 화면 크기가 아니다

**이미지 자체의 가로세로 픽셀 수**이며, **2K·4K 와 같은 종류의 단위**다
(2K = 2048px, 4K = 4096px). 같은 것을 다르게 부를 뿐이다.

**변을 2배 하면 넓이는 4배**가 되므로 용량도 4배로 뛴다.

| 해상도 | 픽셀 수 | ASTC 압축 1장 | PBR 3장 |
|---|---|---|---|
| 128px | 16,384 | 4 KB | **12 KB** |
| 256px | 65,536 (4배) | 16 KB | **48 KB** |
| 512px | 262,144 (16배) | 64 KB | **192 KB** |
| 2K | 4,194,304 (256배) | 1 MB | **3 MB** |

**화면 크기와 무관하지만, 화면 크기로 고른다.** 128px 텍스처를 화면에 크게 띄우면
뭉개져 보이므로 **"화면에서 몇 픽셀을 차지하는가"** 에 맞춰 해상도를 정한다.

### 타일링과 아틀라스 — 용량을 줄이는 두 수단

| 방법 | 무엇 | 효과 |
|---|---|---|
| **타일링 (반복)** | 512px 벽돌 텍스처 한 장을 UV 로 8번 반복 | 실효 해상도 4096px 상당의 벽을 **64 KB** 로 덮는다 |
| **아틀라스 (공유)** | 재질 여러 개를 한 시트에 모아 두고 UV 로 골라 씀 | 모델 200개가 **한 세트**를 나눠 쓴다 |
| **단색** | 텍스처 없이 `albedo_color` | **0 바이트** |

**타일링이 곧 "좌표 범위를 지정한다"의 게임판 구현**이다. 직관이 틀린 게 아니라,
픽셀 단위가 아니라 **UV 단위로** 구현되어 있을 뿐이다.

### 라리엔 3D 에서

카메라가 [3축 고정](#피치--요--롤--카메라-회전-3축)이라 **건물이 화면에서 차지하는
픽셀 수가 계산 가능하다.** 쿼터뷰(거리 17m · FOV 75° · 1080p) 기준이다.

| 건물 높이 | 줌 0.5배 | 줌 1배 | 줌 2배 (최대) |
|---|---|---|---|
| 3 m | 62px | 124px | 249px |
| 6 m | 124px | 249px | **498px** |

**자유 카메라라면 플레이어가 벽에 코를 박을 수 있어 2K 를 준비해야 하지만,
고정이면 최대로 확대해도 500px 를 넘지 않는 것이 확정**이다.
이것이 카메라 고정의 배당금 중 하나다.

제작 규격은 `game` 스킬의 `assets-3d.md` §6~§7 에 있다.
**핵심 규칙 하나만 옮기면 — 건물·프롭에 고유 텍스처를 주지 않고 아틀라스를 공유한다.**
머티리얼이 같아야 메시 병합과 `MultiMeshInstance3D` 가 성립하므로,
**고유 텍스처는 용량과 드로우콜을 동시에 잃는다.**

## 밉맵 (mipmap) — 텍스처를 미리 여러 크기로 줄여 놓은 것

**한 장의 텍스처를 절반씩 줄인 사본을 미리 만들어 함께 저장해 두는 것**이다.
멀리 있는 물체에는 작은 사본을, 가까이 있는 물체에는 원본을 쓴다.

```
원본 512×512
  └ 256×256
      └ 128×128
          └ 64×64
              └ 32×32   …  1×1 까지
```

이름은 라틴어 *multum in parvo*("작은 것 안에 많이")의 머리글자 **MIP** 에서 왔다.

### 왜 필요한가 ① — 없으면 멀리서 화면이 지글거린다

원본 512² 텍스처를 화면에서 **10픽셀** 크기로 그린다고 하자.

| | 무슨 일이 벌어지나 |
|---|---|
| **밉맵 없음** | 512개 줄 중 **10개만 뽑아** 읽는다. 카메라가 조금만 움직여도 **다른 줄이 뽑혀** 픽셀이 반짝거린다 |
| **밉맵 있음** | 16×16 짜리 사본을 쓴다. **이미 평균을 낸 값**이라 흔들리지 않는다 |

이 반짝거림을 **셰이더 앨리어싱(shimmer)** 이라 하고, 움직이는 화면에서 특히 눈에 거슬린다.

### 왜 필요한가 ② — 없으면 오히려 느려진다

GPU 는 텍스처를 캐시에 올려 읽는다. 화면에 10픽셀로 보이는 물체가 512² 원본을
읽으면 **캐시에 안 맞아 매번 메모리에서 가져온다**(캐시 미스). 작은 밉맵을 읽으면
캐시에 들어가므로 **메모리 대역폭을 훨씬 덜 쓴다.**

> 🛑 **3D 에서 밉맵은 화질 옵션이 아니라 성능 옵션이다.** 반드시 켠다.

### 용량은 33% 늘어난다

절반씩 줄인 사본을 다 더하면 원본의 **약 1.33배**가 된다.

```
1 + 1/4 + 1/16 + 1/64 + …  =  4/3  ≈  1.33
```

**그런데도 켜는 것이 이득이다** — 저장 용량은 33% 늘지만 **실제로 읽는 양은 줄어들기**
때문이다. 압축과 함께 쓰면 총량도 오히려 작아진다.

| 2048² 텍스처 한 장 (A12 실측) | GPU 메모리 |
|---|---|
| 무압축 · 밉맵 없음 | **16 MB** |
| **ETC2 압축 · 밉맵 있음** | **2.67 MB** |

### Godot 에서 켜는 법

`.import` 파일에서:

```ini
mipmaps/generate=true
```

에디터에서는 텍스처를 선택 → **Import 독 → Mipmaps → Generate** 를 켜고 **Reimport**.

| 쓰는 곳 | 밉맵 |
|---|---|
| **3D 모델의 텍스처** | ✅ **반드시 켠다** |
| 2D UI · 아이콘 (크기가 안 변함) | ❌ 필요 없다 (용량만 는다) |
| 픽셀아트 (또렷해야 함) | ❌ 끄고 `TEXTURE_FILTER_NEAREST` 를 쓴다 |

### 관련 — 이방성 필터(anisotropic filtering)

밉맵은 "정면에서 본 축소"에는 잘 맞지만, **비스듬히 누운 바닥**에서는 너무 흐려진다.
이때 각도를 고려해 더 선명하게 읽는 것이 이방성 필터다.

```gdscript
m.texture_filter = BaseMaterial3D.TEXTURE_FILTER_LINEAR_WITH_MIPMAPS              # 기본
m.texture_filter = BaseMaterial3D.TEXTURE_FILTER_LINEAR_WITH_MIPMAPS_ANISOTROPIC  # 더 선명·더 비쌈
```

저사양에서는 **바닥처럼 넓게 누운 면에만** 이방성을 쓰고, 캐릭터처럼 작게 보이는 것에는
기본 필터를 쓴다(A12 실측 기준).

관련 → [해상도와 용량](#128px--256px--512px-은-화면-크기가-아니다) ·
[하이폴리 · 로우폴리 · 베이킹](#하이폴리--로우폴리--베이킹--노멀맵을-굽는다)

## 노멀 (normal) — 면이 향한 방향

우리말로 **법선(法線)**. 수학에서 **어떤 면에 수직인 선**을 뜻하는 말이 그대로 넘어왔다.
3D 에서는 **그 면이 어느 쪽을 바라보고 있는가**를 가리키는 **길이 1 짜리 벡터**다.

```
      ↑ 노멀 (0, 1, 0)         바닥면은 위를 향한다
 ───────────────

   노멀 (0, 0, 1) →            벽면은 앞을 향한다
   │
```

### 왜 중요한가 — 조명이 전적으로 여기에 달려 있다

**빛의 방향과 노멀이 이루는 각도가 밝기를 결정한다.**

| 노멀이 빛을 | 결과 |
|---|---|
| 정면으로 향함 | 가장 밝다 |
| 비스듬히 향함 | 중간 |
| 등짐 | 어둡다 |

그래서 **노멀을 속이면 조명도 속는다.** 실제 모양은 평평한데 노멀만 울퉁불퉁하게 주면
**엔진은 울퉁불퉁한 표면인 줄 알고 음영을 계산한다.** 이것이 노멀맵의 원리다.

### 같은 메시가 각져 보이거나 매끄러워 보이는 이유

노멀을 **면마다 하나씩** 주느냐 **꼭짓점마다** 주느냐의 차이다. 형태는 똑같다.

| | 플랫 셰이딩(flat) | 스무스 셰이딩(smooth) |
|---|---|---|
| 노멀 | 면 하나에 하나 | 꼭짓점마다, 면 사이를 보간 |
| 보이는 것 | **각진 다면체** | **매끄러운 곡면** |
| 쓰는 곳 | 로우폴리 아트, 보석·수정 | 사람·동물·구체 |

Godot 의 CSG 프리미티브에는 `smooth_faces` 속성이 있고 **구·원기둥·도넛은 기본 `true`**,
`CSGPolygon3D` 만 기본 `false` 다. `CSGShape3D` 의 `autosmooth`(기본 `false`)를 켜면
`smoothing_angle`(기본 `50.0`)보다 완만한 모서리만 자동으로 매끄럽게 처리한다.

## 노멀맵 (normal map) — 표면 요철을 텍스처에 담은 것

**픽셀마다 노멀 방향을 색으로 저장한 이미지**다. RGB 세 채널이 벡터의 XYZ 에 대응한다.

| 채널 | 담는 값 |
|---|---|
| R | 노멀의 X |
| G | 노멀의 Y |
| B | 노멀의 Z |

**노멀맵이 연보라색인 이유**가 여기 있다. 평평한 면의 노멀은 `(0, 0, 1)` 이고,
이를 색 범위(`0~1`)로 옮기면 `(0.5, 0.5, 1)` — 바로 그 연보라색이다.
그 기준에서 벗어난 픽셀만 표면이 기울어진 것으로 계산된다.

### 실루엣은 바뀌지 않는다 — 노멀맵의 한계

**메시 자체는 그대로다.** 음영만 속이는 것이라,

- 정면에서 보면 → 요철이 있는 것처럼 보인다 ✅
- **옆에서 스치듯 보면 → 그냥 평평하다** ❌
- 요철이 그림자를 드리우지 않는다 ❌

깊은 굴곡이나 튀어나온 부분은 노멀맵으로 못 만든다. 그건 실제 지오메트리로 해야 한다.

## 삼각형 수 · 폴리곤 수 · 정점 수 — 모델의 "무게"를 세는 세 가지 단위

**"캐릭터 하나가 얼마나 무거운가"를 말할 때 쓰는 정확한 용어는 「삼각형 수(triangle count)」다.**
현장에서는 「폴리곤 수」와 섞어 쓰지만, 셋은 서로 다른 것을 센다.

| 용어 | 영문 | 무엇을 세나 | 언제 쓰나 |
|---|---|---|---|
| **삼각형 수** | triangle count · **tris** | GPU 가 실제로 그리는 삼각형 | ✅ **성능 예산의 기준.** 가장 정확하다 |
| 폴리곤 수 | polygon count · **폴리곤·폴리** | 다각형 면(사각형일 수도 있다) | 모델러가 말할 때. **모호하다** |
| 정점 수 | vertex count · **verts** | 꼭짓점 | **스키닝·정점 셰이더 비용**의 기준 |
| 메시 수 | mesh count | 메시 **오브젝트**의 개수 | 드로우콜을 셀 때 (전혀 다른 것) |

### 왜 "삼각형 수" 가 기준인가

**GPU 는 삼각형만 그린다.** 사각형(quad) 면은 렌더링 직전에 삼각형 2개로 쪼개진다.
그래서 "폴리곤 1,000개" 는 삼각형 1,000개일 수도, 2,000개일 수도 있어 **예산으로 쓸 수 없다.**

```
사각형 면 1개(폴리곤 1)  →  GPU 에서는 삼각형 2개
   ┌─────┐                    ┌─────┐
   │     │        ⇒           │ ＼  │
   └─────┘                    └─────┘
```

Blender 의 Decimate 는 **면(face) 수**를 목표로 받고, Godot 의 `surface_get_arrays()` 로
세면 **삼각형 수**가 나온다. 두 값이 다를 수 있으니 **어느 쪽을 말하는지 밝혀야 한다.**

### 정점 수를 따로 봐야 하는 경우

**스킨드 메시(뼈로 움직이는 캐릭터)** 는 정점마다 본 가중치를 계산하므로
비용이 **삼각형이 아니라 정점 수**에 비례한다. 같은 삼각형 수라도
UV 이음매·각진 면이 많으면 정점이 훨씬 많아진다.

> 🛑 다만 A12 실측에서 스킨드 캐릭터 30명의 진짜 병목은 정점도 삼각형도 아닌
> **본 개수**였다 → [lowend-3gb-60fps.md §6](lowend-3gb-60fps.md)

### 캐릭터 삼각형 예산 (모바일 3D MMORPG · A12 실측 기준)

| 등급 | 삼각형 수 | 쓰임 |
|---|---|---|
| 원거리 NPC · 군중 | 1,500 ~ 3,000 | 화면에 수십 명 |
| **일반 NPC** | **5,000** | 이 프로젝트의 NPC 값 |
| **플레이어 캐릭터** | **15,000** | 화면 중앙에서 가장 크게 보인다 |
| 하이폴리 원본 | 50,000 ~ 100만 | **게임에 넣지 않는다.** 노멀맵을 굽는 원본 |

**말하는 법**

- ✅ "이 NPC 는 **삼각형 5,000개**다" / "**tris 5k**"
- ✅ "캐릭터 **폴리곤 예산**이 5,000이다" (관용적으로 통한다)
- ⚠️ "메시 수가 5,000" — **틀린 말.** 메시 수는 오브젝트 개수다

관련 → [하이폴리 · 로우폴리 · 베이킹](#하이폴리--로우폴리--베이킹--노멀맵을-굽는다)

## 하이폴리 · 로우폴리 · 베이킹 — "노멀맵을 굽는다"

3D 에셋 제작의 표준 흐름이며, **폴리곤을 줄이면서 사실적인 외형을 유지하는 방법**이다.

| 용어 | 뜻 |
|---|---|
| **폴리곤(polygon)** | 메시를 이루는 다각형 면. 보통 삼각형 수로 센다 |
| **하이폴리(high-poly)** | 삼각형 수백만 개짜리 **정밀 모델**. 실시간 렌더링은 불가능하다 |
| **로우폴리(low-poly)** | 삼각형 수천 개짜리 **게임에 실제로 넣는 모델** |
| **베이킹(baking, 굽기)** | 계산 결과를 **미리 구해 텍스처 파일로 굳히는 것** |

### 전체 흐름

```
① 하이폴리 조각          Blender·ZBrush 에서 주름·나사·상처까지 실제 형태로 판다
        │                  (삼각형 200만 개 — 게임에 못 넣는다)
        │  베이크
        ▼
② 노멀맵 텍스처          하이폴리의 표면 굴곡을 "방향 정보"로 계산해 이미지로 저장
        │
        │  머티리얼에 입힌다
        ▼
③ 로우폴리 + 노멀맵      삼각형 8천 개짜리 모델이 200만 개짜리처럼 보인다
```

**"하이폴리에서 노멀맵을 구워 로우폴리 메시에 입힌다"** 는 문장은 이 세 단계를 말한다.
정밀 모델은 **최종 결과물이 아니라 텍스처를 뽑아내기 위한 재료**로만 쓰이고,
게임에 들어가는 것은 가벼운 로우폴리다.

**모바일에서 이것이 필수인 이유** — 폴리곤은 GPU 예산을 직접 먹지만 노멀맵은 텍스처
한 장이다. 라리엔 3D 처럼 모바일을 노리는 프로젝트에서 디테일을 확보하는 사실상
유일한 방법이다.

### Godot 에서 쓸 때 (엔진에서 확인)

| 속성 | 기본값 | 주의 |
|---|---|---|
| `normal_enabled` | **`false`** | 🛑 **텍스처만 넣고 이걸 안 켜면 아무 일도 일어나지 않는다** |
| `normal_texture` | — | 노멀맵 이미지 |
| `normal_scale` | `1.0` | 요철 강도. 음수를 주면 파인 곳과 튀어나온 곳이 뒤집힌다 |

```gdscript
var mat := StandardMaterial3D.new()
mat.normal_enabled = true                                    # ← 이걸 빠뜨리면 안 보인다
mat.normal_texture = load("res://assets/wall_normal.png")
mat.normal_scale = 1.0
```

> ⚠️ **노멀맵에는 두 가지 규약이 있다.** Godot 은 **OpenGL 규약(Y+)** 을 쓴다.
> DirectX 규약(Y−) 으로 만든 텍스처를 그대로 넣으면 **요철이 반대로 파여 보인다.**
> 그럴 때는 **G(초록) 채널을 반전**하거나 OpenGL 규약으로 다시 출력한다.

머티리얼 속성 전체와 Bent Normal(4.7) 은 [rendering-3d.md](rendering-3d.md),
임포트 설정은 [resources-assets.md](resources-assets.md) 를 본다.

### ⚠️ "굽는다(bake)"는 세 군데에서 다른 것을 가리킨다

같은 말이 서로 다른 작업을 뜻하므로, 문맥을 보고 무엇을 굽는 것인지 가려야 한다.
**공통점은 "실시간으로 계산하면 비싼 것을 미리 계산해 파일로 굳힌다"** 는 것이다.

| 무엇을 굽나 | 결과물 | 어디서 | 왜 |
|---|---|---|---|
| **노멀맵 베이크** | 텍스처 이미지 | Blender·Substance 등 **외부 도구** | 하이폴리 굴곡을 로우폴리에 입히려고 |
| **CSG 베이크** | `ArrayMesh` · `ConcavePolygonShape3D` | Godot — `bake_static_mesh()` / `bake_collision_shape()` | CSG 는 런타임 CPU 계산이라 그대로 출시하면 안 되므로 |
| **라이트맵 베이크** | 라이트맵 텍스처 | Godot — `LightmapGI` | Mobile 렌더러엔 실시간 전역 조명이 없으므로 |

CSG 베이크는 이 문서의 [CSG 의 제약](#반드시-알아야-할-제약--csg-는-최종물이-아니다) 항목,
라이트맵은 [rendering-3d.md](rendering-3d.md) 에 있다.

## 반드시 알아야 할 제약 — CSG 는 최종물이 아니다

CSG 는 **런타임에 CPU 가 매번 메시를 실시간 계산**한다. 상자 하나 움직일 때마다 전체가
재계산되므로, 그대로 출시하면 **모바일에서 프레임을 그대로 잃는다.**

다만 Godot 4.7 에는 **구워서 일반 메시로 굳히는 API** 가 있다 (엔진에서 확인):

```gdscript
var mesh: ArrayMesh = csg.bake_static_mesh()                    # 시각 메시로 확정
var shape: ConcavePolygonShape3D = csg.bake_collision_shape()   # 콜리전으로 확정
```

그래서 실제 흐름은 이렇게 된다:

```
CSG 로 짓는다 → 걸어보며 고친다 → 확정되면 bake → CSG 노드 삭제
                                              ↓
                              나중에 Blender/GridMap 아트로 교체
```

> ⚠️ **구운 메시에는 라이트맵용 UV2 가 딸려 오지 않는다.**
> [SSOT §2](../../game/references/SSOT.md) 대로 조명을 전부 굽는 프로젝트에서는
> 베이크 직후 **UV2 언랩을 한 번 더 돌려야** `LightmapGI` 가 그 메시를 구울 수 있다.
> 에디터에서는 메시를 선택하고 **`Mesh > Unwrap UV2 for Lightmap/AO`**,
> 코드에서는 `ArrayMesh.lightmap_unwrap(transform: Transform3D, texel_size: float)` 다 (엔진에서 확인).

**블록아웃은 버릴 것을 전제로 빠르게 만드는 단계다.** 예쁘게 만들려고 시간을 쓰면
목적에서 벗어난다. 회색 상자인 채로 **"이 던전 재미있나?"에 답이 나오면 그 단계는 성공**이다.
