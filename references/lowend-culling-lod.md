# 저사양 폰에서 "그리는 양"을 줄이는 6가지 엔진 기능

> **이 문서로 오는 상황** — LOD·가시 범위·오클루전·해상도 스케일링·VRS 를 **쓸지 말지** — 엔진 기능별 저사양 판정

> Godot 공식 문서 6편을 **3GB RAM 폰 · 3D MMORPG** 기준으로 골라 정리한 것이다.
> 원문은 "이 기능이 무엇인가"를 말하고, 이 문서는 **"우리 기기에서 쓸 것인가"** 를 말한다.
>
> 실측 기기 — **Galaxy A12 (SM-A125N)** · 2.8GB RAM · PowerVR Rogue GE8320 · Mobile 렌더러
> 함께 읽기 — [lowend-3gb-60fps.md](lowend-3gb-60fps.md) (실측·베이킹·병목 진단) ·
> [performance-mobile.md](performance-mobile.md) §0 (최소 지원 사양)

## §0 결론 먼저 — 6개 중 넷을 쓰고, 하나는 조건부, 하나는 못 쓴다

| # | 기능 | 무엇을 줄이나 | A12 에서 | 판정 |
|---|---|---|---|---|
| 1 | **MultiMeshInstance3D** | 드로우콜 | ✅ 된다 | ✅ **쓴다** — 단 청크로 쪼갠다 |
| 2 | **Mesh LOD** | **삼각형** | ⚠️ **줌에만 반응** | ✅ **쓴다** — 줌 아웃 대비 (§3) |
| 3 | **Visibility Ranges (HLOD)** | 드로우콜 + 삼각형 | ✅ 된다 | ✅ **쓴다** — 페이드는 끈다 |
| 4 | **해상도 스케일링** | **픽셀** | ✅ Bilinear 만 | ✅ **쓴다** — 가장 값싼 카드 |
| 5 | **Occlusion Culling** | 드로우콜 + 삼각형 | ⚠️ CPU 를 먹는다 | ⚠️ **조건부** — 실내·협곡만 |
| 6 | **VRS** | 픽셀 | 🛑 **하드웨어 미지원** | 🛑 **못 쓴다** |

**⑥ VRS 는 켜도 아무 일도 일어나지 않습니다.** 에러도 경고도 없이 조용히 무시되므로
"켰으니 빨라졌겠지" 하는 **성능 착시**가 가장 위험합니다 (→ §7).

### 🛑 이 게임은 **직교 투영**이다 — 그래서 ②가 다르게 동작한다

카메라가 `PROJECTION_ORTHOGONAL` 고정입니다
([SSOT §1](../../game/references/SSOT.md), 🛑 불변).
**직교에서는 멀리 있는 것도 같은 크기로 보이므로, 거리가 LOD 에 아무 영향을 주지 않습니다.**

| | 원근이었다면 | **직교 (이 게임)** |
|---|---|---|
| Mesh LOD 를 움직이는 값 | 거리 · FOV · 해상도 | 🛑 **`size`(줌) · 해상도뿐** |
| 화면 안 물체들의 LOD | 앞뒤가 **다르다** | **전부 같다** |
| LOD 가 바뀌는 순간 | 카메라가 움직일 때마다 | 🛑 **줌을 조작할 때만** |
| MultiMesh 의 "LOD 통일" 제약 | ❌ 손해 | ✅ **무해** — 어차피 전부 같다 |
| 실측 방법 | 카메라를 움직이며 | 🛑 **줌을 최대로 뺀 상태에서** |

**나머지 다섯 기능(①③④⑤⑥)은 투영 방식과 무관합니다.**

## §1 어느 기능이 어느 예산을 줄이는가 ← 이 문서의 뼈대

저사양의 예산은 **세 축**입니다 ([lowend-3gb-60fps.md §5.3](lowend-3gb-60fps.md)).
**기능마다 치는 축이 다르므로, 병목이 아닌 축을 줄이면 프레임이 1도 안 오릅니다.**

```
        ┌─────────────┬──────────────────┬─────────────┐
        │  ① 드로우콜  │  ② 삼각형·픽셀    │  ③ 메모리    │
        │    (CPU)    │      (GPU)       │   (RAM/VRAM) │
        ├─────────────┼──────────────────┼─────────────┤
MultiMesh    ✅ 줄인다  │  ❌ 안 줄인다      │  ✅ 줄인다
Mesh LOD     ❌        │  ✅ 삼각형        │  ❌
HLOD         ✅        │  ✅ 삼각형        │  ❌
해상도 스케일  ❌        │  ✅ 픽셀          │  ✅ 약간
오클루전      ✅        │  ✅ 둘 다         │  ❌ (CPU 를 더 씀)
VRS          ❌        │  ✅ 픽셀          │  ❌
```

### 🛑 이 프로젝트가 실제로 겪은 것

| 실험 | FPS | 무엇을 알았나 |
|---|---|---|
| 기준 | 40.3 | — |
| **해상도 60%** | 44.2 | 픽셀은 병목이 **아니었다** (+3.9 뿐) |
| **애니메이션 정지** | **59.8** | ✅ **CPU 스켈레톤이 범인** |
| 캐릭터 숨김 | 60.0 | 렌더는 정상 |

그리고 그 뒤 기물을 늘렸을 때:

| | 드로우콜 | 삼각형 | FPS |
|---|---|---|---|
| 기준 | 75 | 101,731 | 60 |
| 기물 추가 후 | 83 (**+8**) | 155,931 (**+53%**) | **56** |

**드로우콜은 8밖에 안 늘었는데 4프레임을 잃었습니다. 범인은 삼각형이었습니다.**
→ 이 상황에서 MultiMesh(①번 축)를 아무리 써도 프레임은 안 옵니다. **필요한 것은 ② 축 —
Mesh LOD 였습니다.**

> **먼저 재고, 그 축을 치는 기능을 고른다.** 순서가 반대면 시간만 버립니다.

## §2 MultiMeshInstance3D — 드로우콜을 줄인다

같은 메시를 여러 벌 그릴 때, 인스턴스마다 **변환 행렬(위치·회전·크기)만** 다르게 두고
**드로우콜 1회**로 그립니다. 크기가 제각각이어도 됩니다 — 스케일은 그 행렬 안에 들어갑니다.

### 에디터에서 뿌리는 법 — Populate Surface

노드 셋이 필요합니다.

| 노드 | 역할 |
|---|---|
| **MultiMeshInstance3D** | 결과가 담길 노드 |
| **Target Surface** | 뿌릴 바닥 (지형 메시) |
| **Source Mesh** | 복제할 것 (나무 1그루) |

`MultiMeshInstance3D` 선택 → 툴바 **MultiMesh** → **Populate Surface**

| 항목 | 쓰임 |
|---|---|
| `Mesh Up Axis` | 소스 메시의 위쪽 축 (누워서 심기면 이것) |
| `Random Rotation` | 위 축 기준 무작위 회전 — **같은 나무 티를 지운다** |
| `Random Tilt` | 전체 기울기 무작위 |
| `Random Scale` | 크기 무작위 |
| `Amount` | 개수 |

다 뿌린 뒤 **Source Mesh 노드는 지워도 됩니다.**

### 🛑 맵 전체를 하나로 묶지 않는다

MultiMesh 는 **인스턴스를 하나씩 잘라내지 못합니다.** 공식 문서 원문입니다.

> there is no *screen* or *frustum* culling possible for individual instances.
> This means, that millions of objects will be *always* or *never* drawn

```
[맵 전체를 MultiMesh 1개 — 나무 5,000그루]
  화면에 보이는 건 100그루 → 5,000그루 전부 GPU 로    ❌ 50배 헛그림

[청크마다 MultiMesh 1개]
  화면에 걸친 청크 3개만    → 약 150그루               ✅
```

**청크 하나에 수십~수백 개가 들어가므로 드로우콜은 이미 충분히 적습니다.**
이 프로젝트의 청크는 32m 이고, 화면에 동시에 걸치는 청크가 **4~9개**가 되도록 잡습니다.

> 함정 셋(컬링·LOD·삼각형)의 상세와 메모리 400배 계산은
> **[lowend-3gb-60fps.md §5.3](lowend-3gb-60fps.md)** 에 있습니다.

## §3 Mesh LOD — 🛑 직교 투영에서는 작동 방식이 다르다

> **2026-09-02 전면 수정.** 이 절은 처음에 **원근 투영을 전제로** 쓰였다.
> 이 게임의 카메라는 **직교 고정**(`PROJECTION_ORTHOGONAL`)이며
> [game 스킬 SSOT §1](../../game/references/SSOT.md) 에 **🛑 불변**으로 못박혀 있다.
> 직교에서는 LOD 의 동작이 **근본적으로 달라진다.**

`meshoptimizer` 가 임포트할 때 LOD 를 만들어 주므로 **손으로 만들 필요는 없습니다.**
엔진이 매 프레임 알아서 고릅니다. 문제는 **무엇을 보고 고르는가**입니다.

### 🛑 직교에서는 "거리"가 LOD 에 아무 영향도 주지 않는다

공식 문서가 밝힌 선택 기준입니다.

> mesh LOD selection uses a **screen-space metric**. This means it automatically takes
> **camera field of view** and viewport resolution into account.

**직교 투영에는 field of view 가 없습니다.** 거리를 바꿔도 크기가 안 변하기 때문입니다.
Godot 도 이것 때문에 한 번 터졌습니다 — 직교 뷰에서 **항상 최저 LOD 만 나오는 버그**
([#57404](https://github.com/godotengine/godot/issues/57404), 에디터의 Preview Orthogonal
카메라가 원점에서 약 2,000m 떨어져 있어서). 고친 방식이 답을 그대로 보여줍니다
([PR #57419](https://github.com/godotengine/godot/pull/57419)) — **직교면 거리를 상수
`1.0` 으로 박고 계산에서 빼 버립니다.**

```
[원근]  LOD = f(거리, FOV, 해상도)     → 멀수록 낮은 LOD
[직교]  LOD = f(size, 해상도)          → 🛑 거리는 계산에 없다
```

**화면 안의 나무 100그루가 전부 같은 LOD 로 그려집니다.** 발밑이든 화면 끝이든
같습니다. 직교에서는 **실제로 같은 크기로 보이므로 그것이 맞는 동작**입니다.

### 그러면 LOD 는 언제 바뀌나 — 줌뿐이다

직교에서 LOD 를 움직이는 값은 **카메라 `size`(= 줌) 하나**입니다.

| 줌 | `size` (데스크톱 기준) | 보이는 범위 | 화면 속 물체 수 | LOD |
|---|---|---|---|---|
| **0.5배** (확대) | 11.25 | 20m × 11.3m | 기준 | **높다** (LOD 0) |
| 1.0배 | 22.5 | 40m × 22.5m | **약 4배** | 중간 |
| **2.0배** (축소) | 45 | **80m × 45m** | **약 16배** | **낮다** (LOD 2) |

**줌 0.5 → 2.0 이면 화면 면적이 16배**가 됩니다. 나무가 16배로 늘어납니다.
동시에 나무 하나는 화면에서 **1/4 크기**가 되고, **바로 그 순간 LOD 가 내려갑니다.**

> ### ★ 직교에서 Mesh LOD 의 진짜 가치
> **"멀리 있는 것을 싸게"가 아닙니다.**
> **"줌 아웃할 때 삼각형이 16배로 폭증하는 것을 자동으로 상쇄하는 장치"** 입니다.
> 줌이 유일하게 허용된 카메라 조작인 이 게임에서, **줌 아웃 순간의 프레임 붕괴를
> 막는 사실상 유일한 자동 수단**입니다.

### 🛑 그래서 생기는 실측 함정 — 줌을 고정하고 재면 효과가 0으로 보인다

**줌 1.0 에 고정해 놓고 LOD 를 껐다 켜면 프레임이 안 변합니다.**
LOD 가 안 듣는 것이 아니라 **바뀔 계기가 없는 것**입니다.
원근이었다면 카메라가 움직이기만 해도 LOD 가 계속 갈렸겠지만, 직교는 그렇지 않습니다.

> **LOD 는 반드시 줌을 최대로 뺀 상태(2.0배 · `size 45`)에서 잽니다.**
> 그 지점이 이 게임에서 삼각형이 가장 많은 순간이고, **LOD 가 일하는 유일한 지점**입니다.

### 설정 (사람이 에디터에서 적용)

| 어디 | 기본 | 뜻 |
|---|---|---|
| `Project > Rendering > Mesh LOD > LOD Change > Threshold Pixels` | **1.0** | **높일수록 성능 우선** |
| `GeometryInstance3D > LOD Bias` | **1.0** | 물체 하나만 예외를 줄 때 |
| `Viewport.mesh_lod_threshold` | 런타임 | 뷰포트별로 따로 |

> **저사양 권장 2.0 ~ 4.0.** 단 근거가 바뀝니다 — "원거리라 안 보인다"가 **아니라**
> **"줌 아웃 상태에서 물체가 실제로 작다"** 입니다.
> **줌을 뺀 상태에서 눈으로 확인하고 값을 정합니다. 줌 인 상태의 화질이 기준이 아닙니다.**

### 🛑 MultiMesh 의 "LOD 통일" 제약 — 직교에서는 문제가 아니다

공식 문서의 경고입니다.

> all instances will be drawn with **the same LOD level** at a given time

**원근이었다면 이것이 손해입니다** — 발밑 나무와 지평선 나무가 같은 삼각형 수가 되니까요.
**그런데 직교에서는 어차피 화면의 모든 물체가 같은 LOD 입니다.** MultiMesh 로 묶든
안 묶든 결과가 같습니다.

| | 원근 | **직교 (이 게임)** |
|---|---|---|
| MultiMesh 의 LOD 통일 제약 | ❌ 손해 — 청크 분할이 필요 | ✅ **무해** — 어차피 전부 같다 |
| **컬링 "전부 아니면 전무"**(§2) | ❌ 손해 | ❌ **여전히 손해** |

> **청크 분할은 계속합니다.** 이유가 셋에서 **둘(컬링·메모리 지역성)로 줄었을 뿐**이고,
> 그중 컬링이 가장 큰 이유였습니다.

### 주의

| | |
|---|---|
| **스킨드 메시** | 렌더링 오류가 날 수 있다 — 캐릭터는 LOD 대신 **본 수·삼각형 수를 줄인다** |
| **OBJ 파일** | 기본 설정으로는 LOD 가 안 생긴다. **씬으로 재임포트**해야 한다 |
| **CPU 병목일 때** | 효과가 불명확하다 — **삼각형이 병목일 때만** 듣는다 |
| 🛑 **줌 고정 측정** | 직교에서는 **줌을 바꾸지 않으면 LOD 가 아무 일도 하지 않는다** |

## §4 Visibility Ranges (HLOD) — 멀면 통째로 바꿔치기

Mesh LOD 가 **메시 하나를 단순하게** 만든다면, HLOD 는 **여러 개를 하나로 바꿔치기**합니다.

```
가까이  →  집 12채 (개별 노드 12개, 드로우콜 12+)
멀리    →  "마을 덩어리" 메시 1개 (드로우콜 1)
```

### 속성 (GeometryInstance3D)

| 속성 | 뜻 |
|---|---|
| `visibility_range_begin` | 이보다 **가까우면 숨긴다** |
| `visibility_range_end` | 이보다 **멀면 숨긴다** |
| `visibility_range_begin_margin` / `end_margin` | 전환 구간 (히스테리시스 또는 페이드 폭) |
| `visibility_range_fade_mode` | 전환 방식 (아래) |
| `visibility_parent` | 부모가 보이면 자식은 자동으로 숨는다 — **계층 HLOD 를 쉽게 짠다** |

### 🛑 저사양은 `fade_mode = Disabled` 로 둔다

| 모드 | 동작 | 비용 |
|---|---|---|
| **Disabled** | 즉시 전환 (히스테리시스로 깜빡임 방지) | ✅ **가장 빠르다** |
| Self | 알파 블렌딩으로 자기를 페이드아웃 | ❌ **투명 패스**가 생긴다 |
| Dependencies | 자식을 페이드인 (계층 HLOD 용) | ❌ 같음 |

**알파 블렌딩은 저사양에서 비쌉니다.** 투명 패스는 정렬 비용과 오버드로를 부릅니다.
부드러운 전환이 꼭 필요하면 **알파 대신 디더링**을 씁니다 — 더 빠르고 정렬 문제도 없습니다.

### 원거리 LOD 메시는 머티리얼도 싸게

공식 문서가 명시적으로 권합니다 — 먼 거리용 메시에서는
**Normal Map · Rim · Clearcoat 를 끄십시오. 특히 모바일에서.**

> 이 프로젝트는 애초에 **`SHADING_MODE_UNSHADED` + 정점 색**이라 노멀맵을 쓰지 않습니다.
> 이미 이 권고를 만족합니다 ([lowend-3gb-60fps.md §3](lowend-3gb-60fps.md)).

### 🛑 직교에서 HLOD 는 Mesh LOD 보다 중요해진다

`visibility_range_begin/end` 는 **카메라로부터의 실제 거리**로 판정합니다.
**투영 방식과 무관하게 그대로 동작합니다.**

> 직교에서 Mesh LOD 는 거리를 보지 않습니다(§3). **거리로 무언가를 줄이고 싶다면
> 남는 수단은 HLOD 뿐입니다.** 원근에서는 둘이 역할을 나눠 가졌지만,
> 직교에서는 **거리 담당이 HLOD 하나**입니다.

**대신 더 조심해야 합니다.**

| | 원근 | **직교** |
|---|---|---|
| 멀리 있는 것이 사라질 때 | 이미 **작아서** 티가 안 난다 | 🛑 **같은 크기라 눈에 띈다** |

직교에서는 **`visibility_range_end` 를 시야 박스(`size` × 화면비로 정해지는 범위) 밖으로
잡는 것이 안전**합니다. 화면 안에서 물체가 사라지면 그대로 보입니다.

> **직교의 이점** — 원근처럼 지평선까지 무한히 보이지 않습니다. `size` 가 보이는 범위를
> 정하므로 **화면에 들어올 수 있는 물체 수에 상한이 있습니다.** 카메라 `far` 로 자르면
> 그만입니다. 저사양에서 **예산을 세울 수 있다**는 뜻이라 결정적으로 유리합니다.

### 언제 무엇을

| 원하는 것 | 쓸 것 |
|---|---|
| **메시를 덜 상세하게** 만들면 된다 | **Mesh LOD** (자동, 손이 안 간다) |
| **드로우콜을 줄여야** 한다 | **HLOD** (거리별 메시를 손으로 만든다) |
| 둘 다 | **같이 쓴다** — 서로 배타적이지 않다 |

## §5 Occlusion Culling — ⚠️ 조건부

**Embree** 소프트웨어 래스터라이저가 저해상도 버퍼에 오클루더를 그려 두고,
물체의 AABB 가 완전히 가려졌는지 검사합니다. **CPU 에서 돕니다.**

### 켜는 법

1. `Project > Rendering > Occlusion Culling > Use Occlusion Culling` (Advanced 토글 필요)
2. 씬에 **OccluderInstance3D** 추가 → 3D 에디터 상단 **Bake Occluders**
3. 움직이는 물체 제외 → `Bake > Cull Mask` 로 레이어 필터

수동 배치도 됩니다 — `QuadOccluder3D` · `BoxOccluder3D` · `SphereOccluder3D` · `PolygonOccluder3D`

### 🛑 Mobile 렌더러에서 특히 크다 — 그런데 우리는 조건부다

공식 문서의 근거는 강합니다.

> Mobile 렌더러는 **depth prepass 가 없어서** occlusion culling 의 효과가 **가장 크다.**
> 셰이딩 오버드로를 적극적으로 줄인다.

**그런데 이 프로젝트에서 바로 켜지 않는 이유가 둘 있습니다.**

| 이유 | 내용 |
|---|---|
| ① **우리 병목은 CPU 였다** | 스켈레톤 갱신이 범인이었고(§1), 오클루전은 **CPU 를 더 씁니다.** 이미 CPU 가 모자란 상태에서 켜면 **오히려 느려질 수 있습니다** |
| ② **내려다보는 야외** | 카메라가 −45° 로 내려다봅니다. **가릴 것이 별로 없습니다.** 공식 문서가 "도움이 안 된다"고 꼽는 것이 정확히 **평탄한 개방형 씬**입니다 |

### 이득 / 손해 판정

| 이득 | 손해 |
|---|---|
| 실내 (벽으로 나뉜 방이 많다) | **평탄한 야외** ← 우리 기본 |
| 협곡·좁은 골목·건물 밀집 시가지 | 오클루더가 자주 움직이는 동적 씬 |
| 복잡한 3D 씬 | **투명 머티리얼이 많은 씬** |

> **이 게임의 결론** — 야외 사냥터는 **끈다.** 건물이 빽빽한 도시 존이나 던전(별도 맵)에서
> **존별로 켜고, 반드시 켠 전후를 실측해서 판단합니다.** 켠 것 자체를 이득으로 치지 않습니다.
>
> 🛑 **실내 건물은 이 게임에 없습니다** — 모든 건물이 껍데기입니다
> ([game 스킬 design.md](../../game/references/design.md) 결정 1). 그래서 "실내라서 이득"
> 이라는 일반론이 우리에게는 그대로 적용되지 않습니다.

### 카메라 3축 고정이 주는 이점

이 게임은 **피치·요·롤이 전부 고정**입니다([SSOT](../../game/references/SSOT.md)).
플레이어가 볼 각도가 하나뿐이므로 **오클루전 사전 계산을 1세트만** 만들면 됩니다.
8방향 자유 카메라라면 8세트가 필요했을 것입니다.

## §6 해상도 스케일링 — 픽셀을 줄인다 ★ 가장 값싼 카드

3D 만 낮은 해상도로 그리고 화면 크기로 늘립니다.

### 🛑 2D UI 는 영향을 받지 않는다

**HUD · 체력바 · 채팅 · 아이콘은 원래 해상도 그대로입니다.** 3D 만 흐려집니다.
저사양에서 이 기능이 특히 좋은 이유입니다 — **글자가 안 뭉갭니다.**

### 설정

`Project > Rendering > Scaling 3D`

| 항목 | 기본값 | |
|---|---|---|
| `scaling_3d_mode` | **Bilinear** | 🛑 우리는 이것만 쓸 수 있다 |
| `scaling_3d_scale` | **1.0** | 저사양 **0.5 ~ 0.75** |
| `scaling_3d_fsr_sharpness` | 0.2 | FSR 전용 — 우리와 무관 |

### 🛑 FSR 은 Mobile 렌더러에서 못 쓴다

| 모드 | 품질 | 비용 | Mobile 렌더러 |
|---|---|---|---|
| **Bilinear** | 중간 | **최소** | ✅ **된다** |
| FSR 1.0 | 높음 | 중간 | 🛑 Forward+ 전용 |
| FSR 2.2 | 최고 (TAA 내장) | **높음** | 🛑 Forward+ 전용 |

이 게임은 Mobile 렌더러이므로 **선택지는 Bilinear 하나입니다.**
애초에 FSR 은 "비용을 조금 내고 품질을 산다"이므로, **비용을 못 내는 기기에서는
Bilinear 가 맞는 선택**이기도 합니다.

### 실측 — 그런데 우리는 이걸로 못 고쳤다

| | FPS |
|---|---|
| 기준 | 40.3 |
| **해상도 60%** | **44.2** (+3.9) |

**픽셀은 그때 병목이 아니었습니다.** 40% 를 깎았는데 4프레임밖에 안 왔습니다.
이 숫자가 곧 **"fill rate 는 우리 문제가 아니다"** 라는 진단이 됐고, 그래서 다음 실험
(애니메이션 정지 → 59.8)으로 넘어가 진짜 범인을 찾았습니다.

> **해상도 스케일링은 고치는 도구이자 재는 도구입니다.**
> 낮췄는데 안 빨라지면 **픽셀은 범인이 아닙니다.** 가장 먼저 해볼 실험입니다.

### 쓰는 법 — 기기 등급별 고정값

```gdscript
## 프로젝트 규칙: 값은 사람이 project.godot 에 넣고, 런타임 조절만 코드로 한다
func _apply_tier(tier: int) -> void:
    var vp := get_viewport()
    match tier:
        0: vp.scaling_3d_scale = 1.0     ## 상급기
        1: vp.scaling_3d_scale = 0.75    ## 중급기
        2: vp.scaling_3d_scale = 0.6     ## A12 급
```

**프레임을 보고 자동으로 낮추는 것은 권하지 않습니다.** 해상도가 오르내리면
화면이 출렁여 오히려 눈에 거슬립니다. **기기 등급으로 한 번 정하고 고정합니다.**

## §7 VRS — 🛑 우리 기기에서는 못 쓴다

기하는 원래 해상도로 그리고 **픽셀 셰이딩만** 듬성듬성 합니다. 모서리는 선명한 채로
셰이더 비용만 줄이는 좋은 기능입니다. **그런데 하드웨어가 받쳐줘야 합니다.**

### 요구 사양

| | |
|---|---|
| **모바일** | Snapdragon **888 이상** · Dimensity **9000 이상** · Mali-**G615 이상** |
| 데스크톱 | NVIDIA Turing+ · AMD RDNA2+ · Intel Arc+ |
| **미지원** | **Apple GPU** · Raspberry Pi |

**Galaxy A12 = MediaTek MT6765 + PowerVR Rogue GE8320 → 어느 줄에도 없습니다.**
iOS 도 전 기종 미지원입니다.

### 🛑 가장 위험한 점 — 조용히 무시된다

> 지원하지 않는 하드웨어에서는 **VRS 를 켜도 시각적 차이가 없습니다.**

에러도 경고도 없습니다. **"켰으니 빨라졌겠지"** 하고 넘어가면 없는 최적화를 있다고
믿은 채로 개발이 흘러갑니다. 지원 여부는 실행 인자 `--verbose` 로 확인합니다.

> **결론** — 이 프로젝트의 최소 사양(3GB RAM · 2020년급 보급기)에서는 **없는 기능으로
> 취급합니다.** 상급기 전용 옵션으로 나중에 붙일 수는 있지만, **저사양 예산을 세울 때
> 계산에 넣지 않습니다.**

## §9 MMORPG 특유의 문제 — 위 여섯 개로 안 풀리는 것

**§2~§7 은 전부 "기물"의 이야기입니다.** 나무·바위·건물은 이 기능들로 정리됩니다.
그런데 MMORPG 의 진짜 부하는 **다른 플레이어와 몹**이고, 여기엔 위 기법이 거의 안 듣습니다.

| | 기물 | **캐릭터** |
|---|---|---|
| MultiMesh 로 묶기 | ✅ | 🛑 **안 된다** — 포즈마다 꼭짓점이 다르다 |
| Mesh LOD | ✅ | ⚠️ 스킨드 메시는 오류 가능 |
| HLOD | ✅ | ❌ 계속 움직인다 |
| 오클루전 | ✅ | ⚠️ 동적이라 오클루더가 못 된다 |

**캐릭터는 "묶어서" 줄이는 게 아니라 "하나하나를 가볍게" 줄입니다.**

| 수단 | 내용 |
|---|---|
| **본 수를 줄인다** | 손가락 본 제거 등. 우리 실측에서 **CPU 스켈레톤이 최대 병목**이었다 |
| **표시 인원 상한** | 화면에 그릴 캐릭터 수를 정하고, 넘치면 먼 것부터 안 그린다 |
| **거리별 컷** | 멀면 이름표·장비 이펙트·그림자부터 끈다 |
| **애니메이션 갱신 분산** | 먼 캐릭터는 매 프레임 갱신하지 않는다 (프레임당 N명) |
| **임포스터** | 카메라가 **한 각도로 고정**이라 판 한 장이면 된다 |

> 상세와 실측(31명 = 드로우콜 63~83, VAT 검토 기준)은
> **[lowend-3gb-60fps.md §7](lowend-3gb-60fps.md)** 에 있습니다.

## §10 체크리스트

**드로우콜**
- [ ] 반복 기물이 **MultiMesh** 인가 (§2)
- [ ] 그 MultiMesh 를 **맵 전체가 아니라 청크마다** 나눴는가 (§2) 🛑
- [ ] 화면에 동시에 걸치는 청크가 **4~9개**인가

**삼각형**
- [ ] `Threshold Pixels` 를 저사양용으로 올렸는가 (§3)
- [ ] OBJ 를 **씬으로 재임포트**해 LOD 가 실제로 생겼는지 확인했는가 (§3)
- [ ] 🛑 **줌을 최대로 뺀 상태에서** LOD 를 확인했는가 — 직교는 줌에만 반응한다 (§3)
- [ ] 줌 아웃 상태의 화질로 `Threshold Pixels` 를 정했는가 — **줌 인 화질이 기준이 아니다** (§3)
- [ ] 먼 거리 메시에서 **노멀맵·Rim·Clearcoat 를 껐는가** (§4)

**픽셀**
- [ ] `scaling_3d_mode` 가 **Bilinear** 인가 — FSR 은 Mobile 에서 안 된다 (§6)
- [ ] 기기 등급별 `scaling_3d_scale` 을 정했는가 (프레임 따라 흔들지 않는다)

**전환**
- [ ] `visibility_range_fade_mode` 가 **Disabled** 인가 — 알파 페이드는 비싸다 (§4)
- [ ] `visibility_range_end` 가 **시야 박스 밖**인가 — 직교는 멀어도 크게 보여 사라짐이 눈에 띈다 (§4)

**하지 말 것**
- [ ] 🛑 VRS 를 켜 놓고 **효과가 있다고 가정하지 않았는가** (§7)
- [ ] 🛑 야외 사냥터에 오클루전을 **재보지 않고 켜지 않았는가** (§5)
- [ ] 🛑 병목을 재기 전에 기능부터 켜지 않았는가 (§8)
